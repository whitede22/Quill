## 实施回执（Round 22）

四步全部完成，测试计数：selfcheck 296 → **331**、gui_smoke 81 → **96**、
变异 47 → **59**。方案里被实测推翻或补充的地方：

| 方案原定 | 实际做法 | 原因 |
|---|---|---|
| PDF 用「卡片式」版式 | 改为**细横线分隔 + 单字标签缩进** | `QTextDocument` 在 PDF 输出路径下**完全不渲染** `border`/`background`/`border-radius`/`padding`（实测 `<table border>` 与 `<div border>` 一律看不见） |
| PDF 分页未指定手法 | 用 `doc.print_(writer)` | 手工 `painter.scale(DPI/72)` + `drawContents()` 只画出文档开头一小段（200 条 → 1 页；`print_` → 18 页） |
| 未提及字体环境 | 新增 `_ensure_fonts()` 守卫 | `QT_QPA_PLATFORM=offscreen`/`minimal` 下 `QFontDatabase.families()` 为 **0**，产出通篇缺字方块而**文件大小与页数全都正常**。宁缺勿滥：无字体时抛 `PdfFontUnavailable` 拒绝输出 |
| 未提及 Qt 应用类型 | 新增 `_ensure_gui_app()` 守卫 | 无 `QGuiApplication` 时 `QTextDocument()` 让进程**静默消失**（rc=127、零输出）；且 `QGuiApplication.instance()` 在只有 `QCoreApplication` 时返回后者，判空会失效 |
| JSON 导入「只认不填」 | 同左，并加**「识别依据」**界面提示 | 同一文件按不同格式读结果完全不同，用户要知道程序走的哪条路 |

另在排查中**发现并修掉两个与本次改动无关的真实缺陷**（都由「兜底词条的
`source` 也是 `"offline"`」这一同值混淆引起）：

1. `MainWindow._origin_of` 从不读 `fallback_reason` → 常驻状态栏把兜底内容
   说成接口给的。
2. `EntryDetail.show_entry` 用 `source == "offline"` 判出路 → 接口模式下拿到
   兜底内容的用户被指引去「切到接口模式」（一个已经开着的开关）。

## 补充：Round 23 —— 有道单词本（XML）导入与字段回填

上面的方案只覆盖到「认 JSON」，没有第三方格式。Round 23 补上**有道单词本的
XML** 与**字段回填**，测试计数：selfcheck 331 → **346**、变异 59 → **65**。

起因是用户问「能导入有道词典单词本吗」。取证后（按有道的真实结构构造导出文件，
喂给当时的分派器）发现答案不只是「不能」，而是**会污染数据**：XML 落到通用
词表解析器上，8 个标签名被当成词收下、真词一个不剩，而**跳过清单为空**。

| 事项 | 做法 | 依据 |
|---|---|---|
| XML 指纹 | 以 `<` 开头 + `ET.fromstring` 成功 + 根元素本地名 `wordbook` | 只验「是 XML」会把别人的配置文件一并吞掉 |
| 取字段 | 按结构遍历 `item` 的 `<word>` / `<trans>`，**不逐行取词** | 标签名都恰好是合法英文词 |
| `<trans>` 归属 | 含汉字 → `definition_zh`；纯英文 → `definition_en` | 有道不区分中英释义 |
| 词性标记 | **不剥** `vt.` 进 `pos` | 剥了会改掉用户看到的原文 |
| 回填范围 | `ParsedWord.fill` + 写入侧白名单 `_FILLABLE_FIELDS` | 单一裁决点；`source` / `prompt_version` 不许回填 |
| JSON 路径 | 同步改为**也回填**（原「只认不填」作废） | 回填机制既已建好，留两份口径风险更大 |

顺带**发现并修掉一个真实缺陷**（与 XML 无关，恰好就在要改的那个函数里）：
`_confirm_import` 的「识别依据」映射把两个键写成「Quill 导出（纯文本）」，
而解析器返回的是「Quill 文本导出」——**永远匹配不上**，于是本程序自己导出
的文件一直被说成「按普通生词表读的」。这正是「谎报比不报更糟」。映射表已提到
模块级 `_FORMAT_HOW`，并加了一条断言盯着它与解析器不许分家。


## 一、问题诊断（基于实测，不是猜测）

### 1.1 导出侧：能力比界面宣称的多，但没说

按钮写着「导出文本」，点开后系统保存框的文件类型是
`文本文件 (*.txt);;Markdown (*.md)`——**能出 .md，但按钮名只说「文本」**。
用户不点开保存框就不知道有第二个选项，点开了也不知道两者差别。

且**只有两个格式**，没有：

- 能直接给 Excel / WPS 打开的（CSV）
- 能完整备份、原样导回的（JSON）
- 能直接打印或发人的（PDF）

### 1.2 导入侧：支持三种格式，界面一个字没提

`importer.parse_text()` 用文件指纹分派三条路径：

| 指纹 | 解析器 | `source_format` |
|---|---|---|
| 含 `Generated by Quill`，或同时有 72 个 `=` 与 72 个 `-` | `_parse_text_export` | Quill 文本导出 |
| 有 `## N. 单词` 标题行 | `_parse_markdown_export` | Quill Markdown 导出 |
| 其余 | `parse_word_list` | 生词表 |

**「本程序导出的文件可以再导回来」这件事，界面上从未说过。** 用户不知道
自己导出的文件是个能回流的备份；也不知道拖进来的文件会被当成哪种格式读。

唯一的提示出现在**失败之后**（`main_window._import_path` 里「没有认出单词」
那条消息会提一句「如果这是本程序导出的文件，请确认词条行首的编号还在」）
——**成功了不问，失败了才说**。

## 二、导出格式设计（五种）

统一由 `app/core/exporter.py` 提供，签名一律
`export_xxx(entries: list[Entry], title: str) -> str`（PDF 例外，写文件）。

| 格式 | 函数 | 面向场景 | 有损否 |
|---|---|---|---|
| 纯文本 `.txt` | `export_text`（已有） | 打印、贴进任何地方 | 无（但结构是给人看的） |
| Markdown `.md` | `export_markdown`（已有） | 贴进笔记工具、转 PDF | 无 |
| **PDF `.pdf`** | `export_pdf`（新增） | 直接打印、发给人 | 无 |
| **CSV `.csv`** | `export_csv`（新增） | Excel / WPS / Anki | **多值字段有损** |
| **JSON `.json`** | `export_json`（新增） | 完整备份、程序间交换 | 无 |

### 2.1 PDF：用 PySide6 自带能力，零新增依赖

实测确认可行（三条都验过）：

- `QPdfWriter` + `QTextDocument` 能出 PDF，**中文正常**——字体嵌入
  （`MicrosoftYaHei-0-400` / `-700`）、Type0/CID 编码、带 `ToUnicode`
  映射（即可搜索、可复制）
- **页面尺寸要对齐**：`QTextDocument` 的坐标系是按 DPI 物理像素算的，
  直接 `setPageSize(paintRect)` 会让 `font-size:12pt` 在 300 DPI 下被
  解释成极小的相对尺寸——**实测内容只占页面宽度的 1/3**
- **正确做法**：文档按 72 DPI 逻辑坐标排版，`QPainter.scale(DPI/72, DPI/72)`
  映射到物理区域。实测两种缩放策略（`scale` 与 `setWindow/setViewport`）
  都能做到满宽 99%，取更直观的 `scale`
- 排版用 **HTML + CSS**（`QTextDocument.setHtml`），天然支持分页、粗体、
  颜色、缩进

**卡片式排版**（用户已确认）：每词条一块，词头加粗大字 + 音标灰色小字，
英/中/例分行，同义语列表，备注区块 —— 视觉层次对齐现有 Markdown 导出。

**必须验的**（test 的起点，按项目铁律先写断言跑出 FAIL）：
- 中文不出方块 / 不乱码（**读回 PDF 检查字体与编码**，不能只看「文件生成了」）
- 多页分页正确（造 200 条，验 `pageCount() > 1`）
- 内容满宽（扫像素找最右非白列，占比 ≥ 90%）

### 2.2 CSV：扁平，一词一行，同义语合成一格（用户已确认）

- 编码 **`utf-8-sig`**（带 BOM）——不带 BOM 的话 Excel 在中文 Windows 上
  默认按 GBK 打开，**中文全是乱码**，这是 CSV 最常见的坑
- 换行用 `\r\n`（RFC 4180）
- 必须用 `csv` 模块写，不能手拼——字段里有逗号、引号、换行时手拼必错
- **多值字段的编码规则**：同义语合成一格，形如
  `omnipresent（无所不在的）— 强调神明或抽象力量的在场; pervasive（普遍的）`
  - 同义语之间用 `; ` 分隔，内部沿用「词（中文简释）— 差异说明」
  - **这条规则有损**：差异说明里若本来就有 `; ` 会被误切。故 CSV 定位为
    「给人看 / 给表格软件用」，**不承诺无损往返**
- 列：`单词, 音标, 词性, 英文释义, 中文释义, 例句, 例句翻译, 同义语, 备注, 标签`
  - **备注保留换行**（与文本导出同理，用户可能有意分行）；CSV 规范允许
    字段内含换行（包在引号里），Excel 能正确显示
  - 表头用**中文**（用户是中文母语者，导出是给人看的）
- 日期/来源等元数据不进 CSV（表格软件不需要，且会干扰筛选）

### 2.3 JSON：完整容器，且能被导入读回（用户已确认）

- 顶层是对象而非裸数组，带格式标识与版本：

```json
{
  "format": "quill-entries",
  "version": 1,
  "exported_at": "2026-09-28 18:00",
  "count": 2,
  "entries": [ { ...全字段... } ]
}
```

- **带 `format` 与 `version` 是为了导入侧能可靠识别**，也是将来加字段时
  能做版本迁移的前提。**没有版本号的格式，第一次改结构就会变成「旧文件
  读不了」**——这与项目里离线词库 `OFFLINE_SCHEMA_VERSION` 的教训同源。
- 只导出**有意义的字段**：`lemma` / `phonetic` / `pos` / `definition_en` /
  `definition_zh` / `example` / `example_zh` / `synonyms` / `notes` / `tags`
  - **排除** `id` / `created_at` / `updated_at`（本机主键与时间戳，
    导到另一台机器无意义，回填还会撞已有数据）
  - **排除** `prompt_stale` / `fallback_reason`（**运行时字段，本就不入库**，
    见 `Entry` 定义处的说明）——导出它们等于把「上次查词时的临时状态」
    写进备份，导回时是过期信息
- `ensure_ascii=False`（中文可读）+ `indent=2`（可 diff、可手改）
- 换行 `\n`（JSON 文件不需要 CRLF）

### 2.4 导入侧新增：认 JSON

`parse_text()` 的分派加一条，**放在最前**（JSON 的指纹最特异）：

- 判据：`text.lstrip().startswith("{")` 且 `json.loads` 成功 且
  顶层有 `format == "quill-entries"`
- 解析后 `source_format = "Quill JSON 导出"`
- **导入要还原的字段比现有两条路径都多**（现在只还原 `notes`）：
  JSON 路径应把能填的都填上（音标、词性、中英释义、例句、同义语、标签）

这引出一个**现在没有的能力缺口**：`ParsedWord` 目前只有
`word` / `line` / `notes` 三个字段，装不下释义、同义语等。
JSON 导入要真正发挥作用，必须**扩展 `ParsedWord`** 并让 `run_import`
按字段回填。这是一个独立的、有风险的数据写入改动——**必须单独评估，
不能混在「加个导出格式」里悄悄做**（见下方「待决策」）。

## 三、界面上怎么讲清楚（用户已确认「两者都要」）

### 3.1 集中说明：一处「格式说明」

在工具栏/菜单加一个入口，打开一个**只读的说明对话框**，内容：

- **导出**：五种格式各一句话（面向什么场景）、各自长什么样（各给一小段
  真实样例）
- **导入**：能认哪三种（本程序文本导出 / Markdown 导出 / 普通生词表 /
  JSON 导出），**认别的键是「按什么规则取词」**
- 样例必须是**从真实导出函数现算出来的**，不能手写——手写的样例会随
  格式改动而过期，而且它不会被任何断言发现

### 3.2 就地提示

| 位置 | 加什么 |
|---|---|
| 导出对话框 | 每个格式项后面跟一句用途（如「CSV — 可用 Excel 打开」） |
| 导出完成消息 | 说明这是什么格式、适合做什么 |
| 导入核对框 | 已经会说 `source_format`（如「Quill 文本导出」），保持；补一句「识别依据」让用户能判断认错没有 |
| 导入失败消息 | 现在只说纯文本的规则，补上「本程序导出的文件（txt / md / json）都能导回来」 |

## 六、推迟到下一轮：JSON 全字段回填

**决定：本轮不做。** 记录的完整理由，供下一轮直接接手：

**现状**：`ParsedWord` 只有 `word` / `line` / `notes`。所有导入路径
（包括本程序导出的 txt / md）**实际只还原了备注**，释义等一律靠之后再查词。

**做成什么**：扩 `ParsedWord` + 改 `run_import` 的字段回填，让 JSON 能真正
当备份用（换机器一键恢复全部内容）。

**为什么单独一轮**：它改动的是**写库路径**，且会触碰「导入不覆盖用户自有
字段」这条既有约定——正是本项目反复栽跟头的地方（备注被静默抹掉、
「新增分支里写恒为真的备注条件」等）。必须：

- 先写断言跑出 FAIL 取证（「已存在的词条内容一字不改」）
- 让变异测试确认能抓住「导入覆盖了已有内容」
- 规则已定：**已有的一律不动，只新增**（库里没有的词才完整收进来）

**若不做**：JSON 仍是「比 CSV 完整的导出」，但导入只有单词生效。

## 补充：Round 27 —— 第六种导出格式：Anki 制表符文本

导出从**五种**变成**六种**，新增 `anki`（`.txt`，制表符分列）。

### 为什么是 txt 而不是 `.apkg`

`.apkg` 要维护一份 Anki 的内部结构（SQLite + zip + 模型与模板定义），成本高
一个数量级，而用户得到的几乎一样。Anki 自己就能导入制表符文本（选文件即可），
所以先把便宜的那版做出来——这条路的价值在于「**今天就能把生词接进记忆流程**」，
而不是「导出得更完整」。

### 与 CSV 的三处刻意不同

| 点 | CSV | Anki | 理由 |
|---|---|---|---|
| BOM | **带**（`utf-8-sig`） | **不带** | CSV 带 BOM 是为了让 Excel 认出编码；而 Anki 会把 BOM 当成**第一个字段的第一个字符**——第一张卡片的正面会凭空多出一个看不见的零宽字符，用户对比半天也找不出为什么这个词「和别的不一样」 |
| 分隔符 | 逗号（`csv` 模块转义） | **制表符** | 制表符是 Anki 约定的列分隔符，而它**没有转义机制**：字段里的制表符与换行必须**先被消掉**，否则整行列数错位、后面每个字段都串到别人那一列，而 Anki 不会报任何错 |
| 备注换行 | 保留（引号内换行，Excel 认） | 折成 `<br>` | 制表符格式里换行就是换行——它会直接断行，把一张卡劈成两行 |

### 结构

```
#separator:tab
#html:true
#tags column:3
ubiquitous	<i>/juːˈbɪkwɪtəs/</i><br>adj.<br><b>无处不在的</b><br>…	考研 高频
```

- 三列：**正面 / 背面 / 标签**（`ANKI_COLUMNS` 一处定义，说明文案与导出函数都从它派生）
- `#html:true` 让背面里的 `<br>` 被渲染成换行；没有它，用户会在一张卡上看到一堆
  字面的 `<br>`
- 背面**刻意不带任何颜色与字号**：卡片长什么样该由 Anki 的模板决定，写进去的样式
  会在用户换模板时变成一对多余的覆盖。这里只表达结构（`<b>` 与 `<br>`）
- 开了 `#html:true` 之后，中文释义 / 英文释义 / 例句 / 同义语 / 备注里的
  `&` `<` `>` **必须先转义**，否则「read < write」会被当成标签吃掉半截。
  转义函数叫 `_html_escape` 而**不叫** `_pdf_html_escape`：走富文本的出口有两个
  （PDF 排版、Anki 背面），各写一份的代价是实测过的那类问题——一处记得转义
  `&`、另一处忘了，而两边都不会报错
- 正面为空白的词条被**跳过**（否则用户在 Anki 里得到一张没有正面的卡片）
- `export_anki()` 的 `title` 参数在 Anki 格式里**没有任何位置可放**（多一行标题
  就是多一张卡片，塞进标签列会污染用户的标签体系），因此它被刻意忽略；
  签名与其他导出函数对齐，所以这条差异不构成特例。自检里有一条断言拿「换个
  标题产出必须逐字节相同」钉住它

### 收尾时的一条教训

「**刻意不带 BOM**」与「**必须先消掉制表符**」这两条如果不被断言钉住，
它们迟早会被下一个人以「跟 CSV 保持一致」为理由改掉——而改完之后**一切照常
运行**，只是第一张卡片多一个看不见的字符、含制表符的释义整行错位。所以
`selfcheck` 为它们各写了断言，`mutation_check` 里也各有一条变异（把 BOM 加回去、
把 `_flatten` 换掉），确认这些断言真的会失败。

## 补充：Round 28 —— 六种导出全部带上「固定搭配」，JSON 能读回它

新增能力「固定搭配」（`collocations`）之后，导出侧要回答的只有一句话：
**用户花接口额度换来的内容，哪一种格式会把它丢掉？** 判据是「静默丢数据」——
丢在本机看不出，要等打印出来或导进 Anki 才发现。

### 各格式怎么放

| 格式 | 呈现方式 | 取舍 |
|---|---|---|
| 纯文本 | 缩进成两层：`搭  be in charge of（负责）`，例句再缩两格 | 例句**必须比搭配深一层**。同深会被读成「这个词的例句」——而一个词的多条搭配各有各的例句，那样读下来会以为例句重复了 |
| Markdown | 与同义语同款的分组小标题 `- **搭**` + 缩进列表 | 走同一套行内转义（`_md_inline`）；代码段内不转义的老规矩不变 |
| CSV | **追加在最后一列**「固定搭配」，一格压多条 | 列顺序是对外接口：插在中间会让所有按列位置取值的表格模板与脚本**静默错位**。所以只能加在末尾 |
| Anki | 折进背面那一格 | 三列契约（正面/背面/标签）没被破坏——背面里放什么由这张卡自己决定，而搭配恰恰是「这张卡最该背的东西」 |
| PDF | 与纯文本同一套版式 | 靠 `doc.print_(writer)` 分页，不手工算坐标（老坑） |
| JSON | `"collocations": [ {...}, {...} ]` 保结构 | 唯一能**读回来**的形态 |

### JSON：为什么加了字段却不递增 `JSON_VERSION`

`collocations` 是**可缺省**字段，它不改变「怎么读这份文件」：旧文件没有这个键，
读进来就是「这个词条没有搭配」；新文件被旧版本的程序读到，导入侧的字段白名单
只会忽略它。版本号留给**破坏性**变化（改类型、改容器形状、改已有字段的含义）。

同一条判据也解释了为什么 `prompts.py` 那边反过来**必须**递增 `PROMPT_VERSION`
（1 → 2）：那不是文件格式，是「这条内容是哪一版提示词生成的」。少了搭配这一块，
旧词条需要被提示「重查一次」——**标记陈旧 ≠ 缓存失效**，两者是两件事。

### 读回来：两处会静默丢内容的地方

1. **`_json_list()` 的双形态**。`Entry.from_row` 拿到的是**库里的 JSON 文本**
   （需 `json.loads`），`Entry.from_payload` 拿到的是**模型返回的 list**（再
   `json.loads` 抛 `TypeError`，被 `except` 吞成 `[]`）。同一句「解析成列表」
   在这两条路上含义不同，写错了就是**搭配一条不剩地消失、且不报任何错**。
   修法是「能直接用的形态先用，剩下的才去解析」，`selfcheck` 为八种输入形态各写了断言。
2. **导入侧的字段白名单**。`_NESTED_FILL_FIELDS` 里漏登记 `collocations`，
   JSON 导出里的搭配就读不回来——而 JSON 一直被当作「备份」格式，用户会以为
   自己备份全了。所以嵌套字段收成一张表（`JSON_NESTED_FIELDS`），导出与导入
   两处同源，而不是各写一遍 `if name == "synonyms"`。

### 收尾时的一条教训

`mutation_check` 里为六种格式**各**加了一条「丢掉搭配」的变异。理由与 Round 27
那段相同：一处记得带、另一处忘掉的代价是「某一格空了」，而**导出会正常成功、
文件大小页数全正常**。只有把每一条出口都单独破坏一次，才能确认每一格都被断言
盯着——「都加上了」这件事不能靠通读代码来确认。

## 补充：Round 29 —— 导入吃 Word 文档，以及「一行列开的长词表」

### 起因（用户实际遇到的那个文件）

老师的单词表是 `.docx`，正文里 **57 个词挤在一行**、逗号分隔，中间夹着
`live to tell`、`generally speaking`、`look down upon` 三条短语。两处都不通：

1. **后缀不认**：导入对话框与拖拽都只认 `.txt / .md / .json / .xml`；
2. **就算另存成 txt 也导不进**：那一行被 `MAX_WORDS_PER_LINE=6` 判成
   「一行有 62 个词，像是句子不是词条」——**收 0 个词**，只留一行跳过记录。

### `.docx` 怎么读：只用标准库

`.docx` 就是一个 zip，正文在 `word/document.xml`。`zipfile` + `xml.etree`
足够（多一个第三方依赖就多一处打包与裁剪风险）。三条规矩：

- **只读 `word/document.xml`**。页眉、页脚、脚注是同目录下的其它 part，
  一起读进来会让页眉上的公司名变成「生词」。
- **`w:tab` / `w:br` 是空元素**，没有文本。只取 `w:t` 会把两列粘成一个词
  （`apple苹果`、`applebanana`），随后被「第一个汉字之后都是解释」整段切掉。
- **压缩包大小说明不了解压后的体积**：几十 KB 的 zip 能解出几 GB 的 XML，
  所以 zip 内那一条的文件大小要单独把关。

老式 `.doc` 不是 zip，读不动时给的中文提示是「请另存为 .docx」，不是 traceback。

### 「一行列开的长词表」：判据从「每段一个词」放宽到「每段 1–3 个词」

旧判据要求用分隔符列开的**每一段都是单个词**，于是只要夹一条短语
（`live to tell`），整条分支就不成立，整行随即落到 `MAX_WORDS_PER_LINE` 上被判成
句子。放宽之后多出来的那些段由 `_valid_word` 兜底（它本来就只认单个词），
所以**不会写错内容**，最坏是少收，而且会如实进报告。

### 另一处更隐蔽的坑：一行就是一个词组时被截成首词

`picks = [tokens[0]]`（「一行取第一个词」）是给 `apple 苹果`、`1. apple /…/ adj.`
这类行准备的，落到单独占一行的 `live to tell` 上，它会往生词本里写一个 **`live`**
——看着像正常词，用户根本发现不了。现在这种情况如实进跳过报告，用户才知道该把
这条词组收进词组收藏（而不是以为它已经收好了）。

### 一处顺手收掉的「两份定义」

`_WORD_SUFFIXES`（拖拽按后缀分派）与文件对话框的过滤器此前是**两份手写的
字面量**，靠注释约定「要一致」。现在过滤器 `_WORD_FILTER` **从后缀表派生**，
结构上不可能出现「对话框里选得到、拖进来却不认」；自检里另有一条「`.docx`
在后缀表里」钉住这份能力本身，免得哪天被当成多余项删掉。

## 补充：Round 30 —— 一行会被谁拦下，取决于是不是**带标点**

这一段是变异测试逼出来的：把 `MAX_WORDS_PER_LINE` 改成 `9999`（句子阈值形同
虚设），旧断言**照样通过**——因为不带标点的整句已经被**另一条**分支拦下了。
两条路都不收录，用户看到的是同一件事（这一行没进生词本），所以光看行为分不出来；
分得出来的只有**报告里的理由**。把顺序写清楚，判据才知道自己守的是哪一支。

`_words_in_line()` 的判断顺序：

| 一行长什么样 | 谁拦下它 | 报告里怎么写的 |
|---|---|---|
| `happy, glad, joyful`（分隔符列开、每段 1–3 个词） | 分隔符分支，全部取 | —— |
| `live to tell`（整行就是一个纯英文词组） | 词组分支 | 「含空格，像是词组不是单词，未收录」 |
| `She went to the store, and then she bought some milk.`（**带标点**的整句） | 句子阈值（>6 词） | 「一行有 N 个词，像是句子不是词条」 |
| `She went to the store to buy some milk`（**不带标点**的整句） | 词组分支（先到先拦） | 「含空格，像是词组不是单词，未收录」 |
| `apple 苹果` / `1. apple /…/ adj.` | 取第一个词（真正要保的那条兜底） | —— |

第 3、4 行是同一个坑的两副面孔：不带标点时长句的字符集与词组**完全一样**，于是它
先撞上词组分支；`MAX_WORDS_PER_LINE` 只在**带标点**那种上才承重，而真实句子几乎
总带标点。所以自检里两种形态各有断言，变异也按名字前缀同时命中两条（见 README
里「保护的前提会过期」那一段）。


## 补充：Round 31 —— 第七种导出：单词表（只为了能导回来）

导出从六种变成七种，新增 `wordlist`（`.txt`，`词<TAB>中文释义`，一行一条）。

前六种都是「给谁看」：打印、粘走、交出去、进表格、进 Anki、给程序读。第七种是
唯一由**导入**倒推出来的格式——「换机器 / 重装 / 想用新接口把旧词重查一遍」时，
用户手上最该有的是一份只由词条组成的文件。拿纯文本导出去当种子，一半以上的行
都要靠解析器猜。

### 为什么必须没有标题

导入侧逐行过解析器，认不出单词又不像装饰线的行会进「跳过」清单并附一句
「没认出单词：…」。这条规则本来是对的（用户需要知道自己少收了什么），但导出的
标题会正好撞进去：

| 若导出写成 | 导入时发生什么 |
|---|---|
| 第一行写 `英语生词本` | 判成废行 → 报告里一条「没认出单词：英语生词本」 |
| 末行写 `Generated by Quill` | **三个英文词，正好落在 2–4 词区间 → 被当成一条词组收进词组收藏** |
| 末行写 `共 20 条` | 同第一行 |

最后一行那种不是「多一条提示」，是**往用户的数据里塞了一条不是他的东西**，而报告
说的是「导入成功」。所以 `export_wordlist()` 连 `title` 参数都不写进去——它与其他
导出函数保持同一签名，但那个参数在这里没有位置。

### 三条附带决定

- **没有中文释义时只写单词**，不留一个空列：第二列承诺的是中文，末尾多一个制表符
  就是一个看不见的尾巴，用户只会怀疑文件坏了；只写单词仍然是一行合法词条。
- **词组照原样写成两列**（`take off<TAB>起飞`）：解析器在这个形态下认得它是词组，
  导回去仍进词组收藏。这一条单独有断言，因为最容易坏的正是它——一旦退回「取第一个
  词」，`take off` 会变成一条 `take` 进生词本，而报告上说「认出 1 条」。
- **默认文件名带 `_单词表` 后缀**：它和纯文本同为 `.txt`，同名会让人以为刚导的是
  同一种格式（保存框也会弹「已存在，是否覆盖」）。

### 它是种子，不是备份

音标、例句、搭配、备注、标签一概不带，因此它是七种里**唯一不遵守**「导出必须带上
固定搭配」那条判据的格式。这不是给搭配开了个例外，而是这条格式的承诺本来就窄：
它只回答「我原来有哪些词、各自是什么中文意思」。要完整备份用 JSON。

### 顺带修正 Round 30 那张表

Round 30 的表格里 `live to tell` 与「不带标点的整句」两行写的是「含空格，像是词组
不是单词，未收录」。v1.1.0 之后那句话已经不成立：整行 2–4 个纯英文词按词组收下，
超过 4 词才报「超过词组的 4 词上限，像是句子，未收录」。句子阈值仍未移动，只是
理由换了说法。
