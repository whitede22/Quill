### 更正一（P1-4）：**"SQLite 会复用 rowid"不成立**

原文在 P1-4 的"实现上有个坑"里写着：恢复时不能带旧 `id`，因为 SQLite 会把删掉的
行号分给下一个新词条。**实测不成立**——`entries.id` 是
`INTEGER PRIMARY KEY AUTOINCREMENT`，SQLite 用 `sqlite_sequence` 记住用过的最大值，
删行之后那个号不会再发出去（自检里有一条断言专门拿它当反例钉住）。

写代码时按这个理由写下的那条注释，第一次改成了另一条**同样错误**的说法：
"带着旧 id 会 UPDATE 到一行不存在的记录、于是静默落空"。**也不对**：
`upsert()` 的查找条件是 `WHERE lemma = ?`，**根本不按 id 找行**。

站得住的理由是第三条：`entry.id is None` 是 `upsert()` 里**唯一**用得上 `id` 的地方，
它决定"同名声词条已存在时，备注与标签听谁的"。撤销是一份**删除前的快照**，清空 id
让它走"回填"那一支——删除之后用户完全可能又把这个词查了回来、并在上面写了新的备注，
保留快照的 id 会把那句新备注静默盖掉。这与项目里"用户自有字段不被回填覆盖"是同一
条铁律。

> **教训**：换掉一条假声明时，新理由**同样要取证**。这两次都是断言抓出来的——
> 没有写"删除后新插入的 id 不等于被删的那个"和"带一个不存在的 id 写回也会更新到
> 那一行"这两条断言，我会用一个听起来更顺耳的谎替换掉原来那个谎，而代码一行都不用改。

### 更正二（P0-1）：**"粘 10 个词得到 1 条整串记录"这个描述只对了一半**

原文说"粘 10 个词 = 得到 1 条记录，lemma 是那 10 个词拼起来的整串（**或模型自作
主张挑了其中一个**）"。前半句对，后半句在这次取证里没有出现——**贬低或高估都算
谎报**。消融 A23 的探针现在会把它打印出来，`['alpha beta gamma']`，一条整串记录，
与前半句一致。

## 一、查词链路

### P0-1　输入框只会查"整串"，粘一串生词进去只得到一个莫名其妙的词条

**取证**

- `main_window._do_lookup()` 把输入框内容整串交给 `_lookup_word()`，中间没有任何拆分（`app/ui/main_window.py:650`）。
- `dictionary.normalize()` 只在"去掉连字符与撇号后全是字母"时才转小写（`app/core/dictionary.py:16`）。`"hello world"` 带空格，所以连小写化都不会做，整串直接当 lemma 去查缓存、再发给接口。
- 结果：粘 10 个词 = 得到 **1 条**记录，lemma 是那 10 个词拼起来的整串（或模型自作主张挑了其中一个）。**用户以为粘进去就会收 10 个词**，实际只收 1 个，且没有任何提示。

**建议**

输入框识别多词：按空白 / 逗号 / 分号 / 换行拆分，>1 个词时走批量。批量链路**不用新写**——导入那条路（`_start_import()` → `_next_import_batch()`）已经把"分批 / 进度 / 取消 / 失败清单 / 新增·已存在统计"全做好了，直接复用。

要守住的边界：

- **含空格的词组不能盲拆**（`ice cream`、`New York`）。做法：先按整串查一次缓存，命中就当词组；未命中再拆。
- 拆出来的每个词仍要走 `normalize()`，并去重、去空。

**代价** 中。难点不在拆分，在"结果怎么呈现"——详情区现在一次只显示一条。最小做法：批量结束后把"新增 N 条"写进状态栏、刷新列表，未收录的沿用 `_save_failed_list()` 落盘。

**判断** 值得做。这是**用户实际的使用姿势**（读文章时攒一串生词），而现在的行为既不报错也不提示。

### P0-2　设置里校验不了"这个地址到底通不通"

**取证**

- `config.check_config()` 只能校验语法：是不是 `http(s)://` 开头、模型名非空、超时是正数（`app/config.py:226-237`）。
- 格式对但域名写错 / 密钥失效 / 模型名不存在，都要等**下一次查词失败**才暴露——而那时用户早已忘了自己刚改过设置。

**建议**

设置对话框里加一个「测试连接」按钮：发一个最小请求（`max_tokens` 极小），把**服务端返回的原话**显示出来。失败时沿用现成的中文翻译表（401 / 404 / 400 / 422 / 402 / 403 各自的动作提示已经写好了，见 `DETERMINISTIC_STATUS_HINTS`）。

**代价** 低。一个按钮 + 一次 `submit()` 异步请求，错误文案全部现成。

**判断** 值得做，性价比很高。它把"下一次查词失败"提前成"当场就知道"。

## 二、生词本管理

### P0-3　`tags` 是一个"数据库和检索都为它做了工作，用户却摸不到"的字段

**取证**

- `entry.tags` 一路贯通：模型字段（`app/core/models.py:52`）、数据库列、FTS 列（`app/core/db.py:106`）、BM25 权重 **3.0**（`app/core/db.py:112`，与 `notes` 同级）、中文 bigram 索引、JSON 导出字段。
- 但 `grep -rn "tags" app/ui/` 的唯一命中是 `export_dialog.py:65` 里的**样例数据**——界面上没有任何地方能编辑它。

**结论**：搜索时标签参与打分，导出时有这一列，用户却永远只能是空值。这是一个半成品字段。要么给它入口，要么把它从 FTS 里摘出去——权重 3.0 挂在一个恒为空的列上，等于把这一档权重白白浪费。

**建议**（二选一，别拖着）

- **A. 补入口**：详情区"备注"下面加一行标签输入（空格或逗号分隔）；左栏再加一排标签 chip 做筛选。**写入与读取都做才算闭环**。
- **B. 摘掉**：从 `FTS_COLUMNS` 移除 `tags`，`FTS_WEIGHTS` 同步调整，文档里说明"暂不支持标签"。

**代价** A 中（要定标签的分隔与展示格式，以及 chip 的取舍交互）；B 低（但要动 FTS 列集 → **整表重建**，见项目里那条既定约束）。

**判断** 优先 A。"给词分类"本来就是生词本的核心价值之一，而这条路现在是断的。

### P1-4　删除没有撤销

**取证** `_delete_entry()` 弹一次确认框，删完只在状态栏说一句"已删除「X」"（`app/ui/main_window.py:785-812`）。没有回收站、没有撤销。
卡片右上角那个 `×` 只有 20×20（`app/ui/widgets.py:499`），紧挨着卡片正文。

**建议** 删除后在状态栏挂一个「撤销」，保留最近一条被删的 `Entry`，下次删除或关窗时失效。

> **【Round 27 更正】本节原来的"实现上有个坑"写错了。** 原文说"SQLite 会复用 rowid，
> 所以恢复时不能带着旧 `id` 直接 `upsert`"——实测不成立（`entries.id` 带
> AUTOINCREMENT，行号不复用）。但"清掉 `entry.id` 重新插入"这个做法仍然是对的，
> 只是理由不同：`entry.id is None` 是 `upsert()` 里唯一用得上 `id` 的地方，它决定
> "同名声词条已存在时备注与标签听谁的"。详见文首「更正一」。

**代价** 低。

**判断** 值得做。确认框是"事前拦"，撤销是"事后救"，两者互补；对一个"随手删"的高频动作，只靠一个 20px 的按钮加一个模态框，误删迟早发生。

### P2-5　列表 1000 条是硬截断，没有"继续加载"

**取证**

- `LIST_LIMIT = 1000`（`app/ui/main_window.py:106`），超出时只把计数标签改成"已显示 1000 条 · 共 M 条 · 请用搜索缩小范围"。
- `Repository.list_entries(order, limit, offset)` 的 `offset` 参数**已经写好了**（`app/core/repository.py:258`），但 `grep -rn offset app/` 显示除定义处之外**没有任何调用方**。

**建议** 做"滚到底自动追加"或"加载更多"按钮，查询侧现成。

**代价** 中。真正的难点不是查询，是**列表的重载语义**：现在的 `_reload_list()` 是"清空重建"，追加要另走一条路，而 `_selected_card` 的引用管理（`app/ui/main_window.py:598`）与 `setItemWidget` 的重复挂载都要跟着改，会碰到界面测试里几条关于列表的断言。

**判断** **优先级不高，可以不做。** 大多数人生词本到不了 1000 条，而"用搜索缩小范围"是个说得过去的出路提示。这条列在这里是为了说明"`offset` 参数不是漏写的"。

### P2-6　复习主线（属于新功能，不是优化）

README 的「后续可做」已经写了"复习模式（间隔重复）与标记分组"。补充两点：

- **别一上来做 SM-2 算法。** 先做"标记：待复习 / 已掌握"两个状态 + 左栏筛选，这一步就能把"生词本 = 收藏夹"变成"能用的复习工具"。
- 一旦加了这个字段，**导出必须跟着带上**，否则换台机器复习进度就丢了。好消息是 `JSON_ENTRY_FIELDS` / `JSON_EXCLUDED_FIELDS` 那条"并集恰好等于全部字段"的断言会自动把它兜住——这是那个派生设计该拿到的好处。

## 三、导入

### P0-4　一次拖进多个文件，只处理第一个，而且不吭声

**取证** `_pick_drop()` 在循环里**第一个后缀匹配就 return**（`app/ui/main_window.py:1090-1096`）。于是：

- 拖 3 个 `.txt` 进去 → 只导入第一个，另外两个静默消失；
- 拖一个 `.txt` + 一张 `.jpg` → `dropEvent` 先看图片，于是**只弹"设为背景吗"，生词表被完全忽略**（`app/ui/main_window.py:1070-1082`）。

两种都是**静默丢弃**：用户以为拖进去的都处理了。

**建议**（按成本从低到高）

1. **最低成本、必须做**：把"只取第一个"改成"取全部"，然后在后续提示里如实说明"这次共拖入 N 个文件，将依次处理"；或保持只处理第一个，但明确说"其余 N 个已忽略"。
2. 完整做法：依次核对 + 依次导入，把 N 个合并成一次统计。

**代价** 低（做法 1）/ 中（做法 2）。

**判断** 必须先修"不吭声"这件事。**静默忽略是这一类里最该修的**——它不报错、不影响任何断言，只是让用户丢文件。

### P1-7　导入核对框只列 3 行"跳过原因"，大文件没法核对

**取证** `_confirm_import()` 里写的是 `parsed.skipped[:3]`，其余只留一句"…另有 N 行，不再列出"（`app/ui/main_window.py:889-894`）。

**建议** 沿用同文件已有的写法：把完整跳过清单写到文件（`_save_failed_list()` 就是这么做的，`app/ui/main_window.py:1043`），在核对框里给出路径。

**代价** 低（照抄现有实现）。

**判断** 值得做。核对框存在的意义就是"让用户看出文件被理解错了"，而只给 3 行时，用户恰恰看不出全局。

## 四、导出

### P1-8　加一个 Anki 能直接吃的格式

**取证** 现在 5 种格式：纯文本 / Markdown / PDF / CSV / JSON（`app/ui/export_dialog.EXPORT_FORMATS`）。README 已把"Anki .apkg / 墨墨扇贝欧路导出"列为后续可做。

**建议** **先做便宜的那一版**：Anki 自己就能导入"制表符分隔的 txt"（正面 / 背面 / 标签三列）。这几乎等于现有的 `export_csv` 换个分隔符，成本极低，却能立刻把生词接进真正的记忆流程。`.apkg`（sqlite + zip 打包）留到以后——它要维护一份 Anki 的 schema，维护成本远高于收益。

**代价** 低（tab 版）/ 高（apkg 版）。

**判断** 做 tab 版。这条路的**用户价值**与 apkg 几乎一样，**成本**差一个数量级。

### P2-9　PDF 版式不可调，也没法做卡片式

**取证** 现成约束：`QTextDocument` 在 PDF 输出里**完全不渲染 border / background**（项目里已经踩过并写进文档），所以"卡片式"打印稿做不到。

**建议** 在现有版式上加"紧凑 / 宽松"两档行距与字号，比追求卡片式现实得多。

**代价** 中。

**判断** 可以做但不急。**别去做卡片式**——那是已知走不通的方向。

## 五、我建议**不要**做的

| 想法 | 为什么不建议 |
|---|---|
| 把 `QFileDialog` 换成 Qt 自己的对话框（`DontUseNativeDialog`），让深色主题下的文件框也变深 | 原生框自带"最近位置""系统快捷方式""OneDrive 入口"，换成 Qt 版这些全丢。深色主题下文件框是浅色的确不一致，但**系统级 UI 与本程序不一致在用户预期之内**。代价大于收益。 |
| 给离线词库补同义语 | ECDICT 是"词 → 释义"语料，不含近义词关系。拿 `exchange`（词形变化）充当同义语会直接误导——`runs` 不是 `run` 的同义词。这条已写在 `app/providers/offline.py` 的 docstring 里，我认同。 |
| 把中文检索的 bigram 换成外部分词器（jieba 等） | bigram 已经在 20000 条库上把中文查询做到 0.1 ms 量级（消融 A2 实测），拆词只会引入新依赖与新失败模式。**没有性能问题就不要换。** |
| 为一万条以上的词库做"加载更多" | 见 P2-5。参数留着，但不值得为它改列表的重载语义。 |
| 提前上 SM-2 间隔重复算法 | 见 P2-6。没有"标记"这一步，算法没有输入。 |

## 附：这次读代码时顺手确认过、**不用改**的几件事

- 单实例锁、缓存优先、DPAPI 密钥加密、状态栏常驻接入状态——都在正常工作，没找到缺口。
- 导出不被列表上限截断（`unlimited=True`）、`search(limit=None)` 省略 `LIMIT` 子句——这两条曾经是坑，现在是对的。
- 五种导出格式的"格式说明"样例是**现算**的（`format_samples()` 调真实导出函数），不会过期。
- 导入的"识别依据"表与解析器返回的 `source_format` 有断言盯着不许分家（曾经分过家，"本程序导出的文件被说成普通生词表"）。
