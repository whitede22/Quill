# 设计与取证笔记

README 讲怎么用，这份文档讲为什么这么写。里面的每一条保护都对应一个真实发生过的
故障，以及一段我当初取证的过程（哪些是实测数字，哪些是踩坑后才明白的）。

内容按原文迁移，改动前先读它对应的那条测试。

## 设计说明

**查词为何采用三级缓存查找**：按「原形直接命中 → 别名表命中 → 屈折候选回查」的顺序查找。第三级用本地规则提出候选原形（`running` → `run`），逐个回查本地库，命中才采用并写入别名表。由于候选只在库中确实存在时才被采纳，规则可以写得宽松而不会污染数据，因此无需引入 nltk / spacy 这类重型依赖。

**已知限制——屈折候选的同形碰撞**：候选只要在库中命中就会被采纳，所以「表面形式恰好等于某个已收录词的屈折形态」时会答非所问。例如库里收了 `new`，再查 `news` 会直接命中它；`whose` → `who`、`these` → `the` 同理。这类碰撞需要「表面形式与候选原形同形」两个条件同时成立，实际触发概率不高，且规则本身不会污染数据；但这是**已知限制**而非安全边界。真正稳妥的做法是引入词典做回环校验（反向生成屈折形式，验证表面形式确实由该原形派生）——注意即便如此也不能解决 `news` / `new` 这种真同形，需要词典才能判定。

**中文检索为何需要额外处理**：SQLite FTS5 的 `unicode61` 分词器会把中文逐字切开，导致「无处不在」无法命中「无处不在的」。本项目在索引时把中文段切成相邻二字组合（bigram）存入独立列，查询端做同样处理并以 phrase 方式匹配，从而获得正确的子串语义。

**这条链路有多值钱，是量出来的**：消融实验里把它抽掉（查询端不做 bigram 转换）后，**命中结果一模一样**——因为 `search()` 会**静默回退到 `LIKE`**，而 `%关键词%` 同样能命中中文子串。但耗时在 20000 条库上从 **0.1 ms 变成 3.7 ms（约 40 倍）**。所以它的价值是**性能**，不是「能不能搜到」；而这一点必须靠足够大的数据量才量得出来：3000 条时两条路径都在亚毫秒量级，测出来的「快慢」全是抖动（我第一版探针就是这么误判成「bigram 没有性能收益」的）。**探针的数据规模不够，会给出一个方向相反的结论。**

**检索覆盖范围**：英文侧用裸词前缀匹配——FTS5 中不带列名前缀的词会命中**所有列**，因此例句、备注、标签天然被覆盖；中文侧则聚合进 `zh_bigram` 列（中文释义、例句翻译、备注、标签、同义语简释）。刻意**不含**同义语的 `diff_note`：「强调」「侧重」这类词几乎出现在每个词条的差异说明里，纳入后搜这些词会命中整个生词本，是噪音而非召回。`entries_fts` 的列集写成 `db.FTS_COLUMNS` 单一常量，DDL、BM25 权重与升级时的结构比对全部由它派生，避免三者对不齐。

**LIKE 回退路径的字段覆盖必须与 FTS 一致**：索引表损坏或 FTS5 不可用时会退化为 `LIKE` 查询。回退路径的字段若比 FTS 窄，就会出现「索引一坏、检索能力静默退化」——不报错、不崩溃，只是搜不到了。因此两条路径的字段集在改动时必须同步。

反过来说，**正因为回退路径能兜住结果，索引坏掉时用户是察觉不到的**（结果一样，只是慢 40 倍）——这条「静默退化」的通路必须由测试直接守住：`selfcheck` 里有一条断言检查中文查询构造出的 FTS 表达式里**真的出现了 bigram 短语**（形如 `(zh_bigram:"无处不在")`），而不是退化成 `LIKE` 扫全表。这一条是做完消融实验后补的，此前完全没有覆盖。

**导出的换行处理**：机器生成的单值字段（释义、例句、同义语）内部换行只可能是模型输出的噪音，一律折叠为空格；用户手写的备注可能有意分行（记忆法、联想），保留换行且续行缩进对齐到正文位置——否则打印稿里续行会顶到最左侧、看起来脱离了所属词条。`selfcheck` 中有 11 项断言锁住这个版式。

**Markdown 导出要转义，纯文本不转义**：Markdown 会把内容原样交给渲染器，所以备注续行的行首 `-` 会变成列表项、`>` 变成引用、`#` 变成标题，`1.` 还会被渲染器**重新编号**——用户自己写的序号就此消失，且全程无声。因此行内元字符（`` ` `` `*` `_` `\`）与行首结构字符都会被转义，反斜杠在同一次替换中处理以免被二次利用。纯文本是打印路径，不做任何转义（反斜杠会原样打印出来）。另注意反引号代码段（音标）内部**不能**转义：反斜杠在代码段里是字面量，转义反而会显示出来。

**导出不受列表显示上限截断**：列表设 `LIST_LIMIT` 是为界面性能，超出时计数标签会明确写出「已显示 N 条 · 共 M 条」。导出若沿用同一上限，打印稿会被静默砍掉一截，而文件头还自称「共 N 条」——N 恰好是被截断后的数量，用户无从察觉。因此 `_current_entries(unlimited=True)` 与 `search(limit=None)` 专供导出路径使用。

**CSV 必须带 BOM，而且 BOM 要写在返回值里**：不带 BOM 的 UTF-8 CSV 在中日韩 Windows 上会被 Excel 按 GBK 打开，中文释义整片变成乱码。修法的关键不是「记得用 `utf-8-sig` 编码」——那是调用方的事，编码名容易漏，漏了不报错、只在别人的 Excel 里表现为乱码，回不到写代码的人眼前。因此 `export_csv()` 直接把 `\ufeff` 拼进返回值，`_write_export()` 统一用 `utf-8` 落盘。行尾用 `\r\n`（RFC 4180 与 Excel 的期望）。同义语合成一格（`ubiquitous（弥漫的）; omnipresent（无所不在的）`），**是有损的**——CSV 是一词一行的扁平表，把同义语拆成多行会让一条词条占掉好几行，筛选排序立刻失效。所以格式说明里明写了这件事，不让用户自己发现。

**JSON 排除本机字段，且靠派生来守**：导出的 JSON 带 `format` 与 `version`，能被本程序读回，但它**不含** `id`、`created_at`、`updated_at`，也不含 `prompt_stale` / `fallback_reason` / `aliases` 这三个运行时字段。理由是这份文件要能安全地拷到另一台机器：本地自增主键到了那边毫无意义，时间戳会把「导入时间」谎报成「当时查词的时间」，而运行时字段描述的是某一次请求的过程、不是词条本身。字段清单不是手写的两份（`JSON_ENTRY_FIELDS` 与 `JSON_EXCLUDED_FIELDS`），而是从 `Entry` 的字段集**派生**出来的，`selfcheck` 断言两者之并恰好等于全部 18 个字段——漏登记会失败，重复登记也会失败。

**导出与导入的格式标识刻意各写一份**：`exporter.JSON_FORMAT_TAG` 与 `importer._JSON_FORMAT_TAG` 是两个独立常量，值都是 `"quill-entries"`。这不是疏忽——导入侧若 import 导出侧的常量，将来改了标识，**所有旧文件就都读不了了**，而这件事要到用户反馈时才发现。各写一份的代价是可能出现漂移，所以有一条断言专门盯着这两个值相等，漂移了立刻报红。

**JSON 指纹必须三重条件**：以 `{` 开头 + `json.loads()` 成功 + `format == "quill-entries"`，三条缺一不可。只验「它是个合法 JSON」是不够的——别人的 `settings.json`、某个软件导出的配置也会被当成生词本吞进来，而 `entries` 字段不存在时最坏的结果是**静默导入 0 条**，用户以为成功了。任何一步解析失败都返回 `False` 而不是抛异常，让文件退化去走后面的普通词表路径。

**XML 指纹（有道单词本）与 JSON 同构，而且必须按结构取字段**：有道的导出是 `<wordbook><item><word>…</word><trans>…</trans><phonetic>…</phonetic></item></wordbook>`。要命的是它的**标签名恰好都是合法英文词**——`word`、`item`、`trans`、`phonetic`、`tags`、`progress`——所以落到通用词表解析器上会产出 8 个假词条（`xml` / `wordbook` / `item` / `word` / `trans` / `phonetic` / `tags` / `progress`），而真词一个都取不到，**跳过清单还是空的**：用户看到「导入成功 8 个词」，库里装的全是标签名。判据同样是三条缺一不可：以 `<` 开头 + `xml.etree.ElementTree` 解析成功 + 根元素**本地名**是 `wordbook`。只验「是个 XML」会把别人的配置文件一并吞掉。解析必须走**结构**（遍历 `item` 下的 `<word>` / `<trans>`），不能逐行取词——这正是这条路径存在的理由。`<trans>` 中英混排，按「有没有汉字」分派到 `definition_zh` / `definition_en`；刻意不把 `vt.` 这类词性标记剥进 `pos`，那会改掉用户看到的原文。

**PDF 生成需要真实平台的字体引擎，这件事不能靠「文件生成成功」来验证**：`QT_QPA_PLATFORM=offscreen`（无显示环境下的常用技巧）会让 `QFontDatabase.families()` 返回**空列表**——于是所有字符被画成缺字方块，而 **PDF 文件本身正常生成、大小正常、页数正常**。我曾经在自检里 `setdefault("offscreen")` 来保证无界面也能跑，结果是通篇方块而自检全绿。现在 `export_pdf()` 会在无字体时**抛 `PdfFontUnavailable` 拒绝输出**，界面弹「无法导出 PDF」并说明是环境问题、不是词条有问题——**宁可明确报告不出，也不要静默交出一份满屏方块的文件**。自检里对应这条的断言也写成「有字体则验渲染、无字体则明确跳过」，跳过时必须打印原因（实测本机有 354 个字体族，含 `Microsoft YaHei`，走的是验证分支）。

**PDF 的分页必须交给 Qt**：`doc.print_(writer)` 接受 `QPagedPaintDevice`，自动处理分页、DPI 换算与页面尺寸；换成手工 `painter.scale(DPI/72)` + `drawContents()` 只会画出文档开头一小段——实测 200 条词条，前者得到 **18 页**，后者只得到 1 页且后面全丢。另外 `doc.pageCount()` 在 `print_` 路径下**恒为 1**，所以分页断言必须用 `QPdfDocument.pageCount()` 而不是 `QTextDocument.pageCount()`。

**PDF 里画不出边框，所以改用分隔线**：`QTextDocument` 在 PDF 输出路径下**完全不渲染** `border` / `background` / `border-radius` / `padding`——实测给 `<table>` 加 `border:1pt solid #999`、给 `<div>` 加 `border`，在 PDF 里一律看不见。原先设想的「卡片式版式」因此无法实现，改成「细横线分隔 + 单字标签缩进」：词条之间画一条 `#C9C9C9` 的细线，词条内部用「英　/ 中　/ 例　/ 同　/ 注　」这样的全角空格缩进对齐。能用的排版手段只剩字号、字重、颜色、`<br>`、缩进与简单 margin。

**PDF 的验证断言必须先把渲染结果合成到白底**：`QPdfDocument.render()` 在 Python 侧只有 `render(page, size, options)` 一个重载（没有 QPainter 版本），返回 `Format_ARGB32` 且**背景完全透明**——空白处 `alpha=0`、`rgb=(0,0,0)`。直接读 `pixelColor().value()` 会得到 0（纯黑），于是**每一个点都被判成「有墨迹」**，整页都是黑的，任何「内容铺开了没有」的断言都恒为真。必须先 `img.fill(0xFFFFFF)` 再画上去。同一条断言还差点被第二种假象骗过：缺字方块会让非白像素暴增、最右列直接顶到页边，于是「满宽」也恒为真。现在的判据是三条一起看——内容铺开（有墨迹列 ≥ 对应宽度）、**不是被整页涂满**（< 50%，方块会糊死页面）、**确实有内容**（≥ 5%）——阈值按实测留量：正常文字段落的最右只到 83%，那是排版正常、不是代码错。

**左侧列表做成卡片，而不只是「长得像卡片」**：卡片不能仅仅是圆角加底色。列表项自身的选中底色必须让位（`QListWidget::item` 改成透明），否则会在卡片圆角外露出一圈方角底色，看着像卡片没对齐；选中态改由卡片自己画（`QFrame#card[selected="true"]`），而动态属性变化后必须 `unpolish`/`polish`，否则 QSS 匹配不到，表现就是「点了没反应」。列表项的**文本**要保留（`_list_text`）：它被卡片整块盖住，但无障碍接口与测试都靠它读「这一行是什么」，丢掉它卡片就只剩像素。行高用 `item.setSizeHint(QSize(0, EntryCard.HEIGHT))` 与卡片对齐，卡片之间的间隙交给列表的 `setSpacing`，而不是给卡片加外边距——后者要再套一层容器，行高便不再等于卡片高度，`setUniformItemSizes` 的一致性假设会被打破。

**删除为什么要推迟一轮事件循环**：卡片上的删除按钮一点会重建整个列表（`_reload_list()` → `clear()`），而此刻发出 `clicked` 的按钮正压在自己的处理栈上——立刻销毁它属于 Qt 明确不保证的行为。确认框又会开一个嵌套事件循环，让风险更大。因此删除统一走 `_request_delete`，用 `QTimer.singleShot(0, …)` 等按钮的处理栈退干净。详情区的删除按钮也走同一条路径：它当前的容器由 `deleteLater()` 销毁、当场不炸，但那条安全性依赖**另一个类的实现细节**，哪天改成立即销毁就会变成偶发崩溃——同一个动作只留一条路径，才只有一处需要守。

**删一条不该顺手清掉阅读位置**：删除后若详情区显示的正是被删的那条，才清空详情区并落回占位态；删的是别人时用 `_reload_list(select_id=…)` 把正在读的词条选回来。在列表上删一条本该是「随手清掉」，不该把用户的阅读位置一起清掉。

**导入为什么要分四条解析路径**：用户给的文件有不同的出身，必须用不同方式读。**本程序自己导出的**文本/Markdown 文件，每条词条占多行（英 / 中 / 例 / 同 / 注各一行）；若按「每行取第一个词」处理，那些释义行会被当成词条——`seeming`、`becoming` 之类从释义里被挖出来收进生词本。这不是「少收几个词」，是**往用户的数据里写入错误内容**，而且一条词条能带出三五个假词。因此先按文件指纹认出导出格式（末尾的 `Generated by Quill`，或同时具备 72 个 `=` 的头部线与 72 个 `-` 的分隔线），按块解析、只认 `N. 单词` 那一行；**别处整理来的生词表**才走逐行取词。判错的方向是不对称的：把普通词表误判成导出格式只会漏收（看得见、能重来），反过来会写入假词（污染数据、且不易察觉），所以指纹倾向于「像就认」。第三条路径是 **JSON**，第四条是**有道单词本的 XML**——这两条都不靠猜：前者文件里直接写着 `format` 字段，后者根元素是 `<wordbook>`。它们必须排在最前面判断，因为「像就认」的启发式一旦先跑，`"lemma"` 与 `<word>` `<trans>` 这些行就会被当成单词收走。**两条结构化路径都会把释义等字段回填进库**（详见上面 XML 那一段），回填范围由写入侧的白名单统一裁决。

**导入先给识别结果，再写库**：解析终究是在猜（JSON 与 XML 除外），所以写库之前会把「认出多少个、**是按哪种格式认的**、跳过了哪些行、前几个词长什么样」摆出来让用户核对。少了这一步，猜错时用户只能等导入完再去一堆词条里翻找垃圾。**「识别依据」这一行不能省**：同一份文件被当成两种格式读会得到完全不同的结果，用户只有知道程序走的是哪条路，才能判断结果是否可信——看到「按普通生词表读的，每行取第一个英文词」而文件其实是本程序导出的，就该警觉。而这张「格式 → 识别依据」的映射表，与解析器返回的 `source_format` 是**两份定义**，必须有一条断言盯着它们不许分家：分家的后果是**本程序自己导出的文件被说成普通生词表**——这不是假想，那两个键曾经写成「Quill 导出（纯文本）」而解析器返回的是「Quill 文本导出」，于是每一份自家导出文件的识别依据都在说谎，**谎报比不报更糟**。完成后报的是三笔账（新增 / 已存在 / 未能收录），查不到的词连同原因写成清单落在数据目录——只报一句「有 5 条没进来」等于把问题丢回给用户。

**导入只补备注，不覆盖备注**：源文件带备注（本程序导出的文件就带）时，只有该词条**原本没有备注**才写入。备注是用户自己写的东西，导入无权覆盖；而漏填又等于让用户白改一遍——「已有就留着」同时避开这两头。**结构化字段（释义、音标、分类）走的是另一条边界**：它们由 `run_import` 在「本次新增」的词条上直接写入——已有的词条在 `entry.id in known` 处就先 `continue` 掉了，所以不可能覆盖用户数据；而新建行的这些字段虽然由 `lookup()` 填过，但那属于**程序生成的内容**、不是用户写的，用文件里的值覆盖它正是「导入」的本意。哪些字段允许被文件回填，由写入侧的 `_FILLABLE_FIELDS` 白名单**一处裁决**：`source` / `prompt_version` 这类程序元数据不在表内——`source` 被回填等于**谎报来源**（比不报更糟），`prompt_version` 被回填会让「内容来自旧版提示词」的判断错乱。另外「新增」与「已存在」靠导入前的 id 快照判定，不看 `lookup()` 返回的「是否命中缓存」：别名命中（`running` → 已有词条 `run`）同样算缓存命中，把它说成「新增」会让报告里的数字对不上账。

**贴数字的匹配不截出半个词，而且只由一处裁决**：`2fa` 这类串，正则本能地会匹配出 `fa`，于是一行噪音变成一个真词条。挡它的做法**不是**回溯改正（回溯会给出更坏的结果），而是让词的正则本身**根本不含数字**：`_TOKEN_RE` 匹配出的片段天然是字母序列，`word2` 拿到的是 `word`、`2fa` 一个字符都拿不到。

这条规则曾经实现成两道——词的正则一道，外加一句「匹配后面紧跟着数字就整段丢弃」——结果第二道比第一道狠得多：`apple1`、`banana2`、`cherry3` 被整行丢掉，而**「词尾紧跟序号」恰恰是别处导出的词表最常见的格式之一**，整份词表会被收成 0 个词，用户只看到一屏「跳过行」。根因是**同一个属性有两份定义**：一份正确、一份过度，结果由过度的那份说了算。现在只留 `_valid_word()` 一处裁决（`h2o` 这类中间夹数字的形态照样被它挡住）。

同理，一行里出现超过 6 个词、且没有分隔符把它明确列成若干段时，整行按句子跳过：一句自然语言里落单的第一个词只可能是 `She` / `The` 这类东西，宁可少收并如实报告。但「happy, glad, joyful」这种用逗号列开的纯词表**不受阈值限制**，判断顺序必须是「先看分段纯词，再看阈值」。

**提示词版本**：`app/providers/prompts.py` 的 `PROMPT_VERSION` 参与**缓存有效性判定**（不是「缓存键」——本项目没有缓存键）。查词时该版本号随词条落盘到 `entries.prompt_version`；命中缓存时若记录的是更早版本，详情面板会提示「由旧版提示词生成，可重新查询更新」。因此**改动 `SYSTEM_PROMPT` 或输出格式后必须递增该版本号**，否则存量词条不会暴露出「内容按旧标准生成」。

这条链路只负责「让用户知道哪条该重查」，**不会自动重查、也不让缓存失效**：若把陈旧当成未命中，离线时点开已有词条会直接失败，那是把「内容可能是旧的」升级成了「根本看不到」。

此机制曾长期是空头声明——常量被定义并导出，却没有任何代码读取它，文档却写着「参与缓存键计算」。**可读取的假保护比没有保护更危险**，因为维护者会以为版本号已经替自己兜住了。

**「新建库会怎样」不等于「升级库会怎样」**：`CREATE TABLE IF NOT EXISTS` 对已存在的表**不做任何事**，所以往 `entries` 加一列时，老用户的库永远不会多出这一列，随后任何带新列的读写都会失败。这也是给 `prompt_version` 落盘时踩到的第二个坑：当时 `init_db` 的注释写着「新增列无需迁移脚本」，而那是把新建库的行为误当成了升级行为。现在新增列必须登记进 `db.py` 的 `ENTRIES_ADDED_COLUMNS`，由 `_ensure_columns()` 按 `PRAGMA table_info` 比对后 `ALTER TABLE` 补上，并只在补列那一次回填历史值——回填值用常量 `LEGACY_PROMPT_VERSION` 而不是当前版本号，否则未来递增版本号时，老词条会被重新说成新版生成，陈旧提示反而永远不出现。

验证方式同样是「造一个真的旧库」：`selfcheck` 与打包自检都会用 DDL 去掉该列后建库、插入数据、再走一次 `init_db`，断言列被补上、历史行被正确回填、且重复 `init_db` 不会改写已标注的值。

**配置文件必须「坏不坏都不崩」**：`config.json` 是用户可写、也可能被其他工具写坏的文件。它一旦让程序起不来，用户就**没有自救手段**了——软件打不开，也就没有界面可以把设置改回来。因此 `load_config()` 承诺绝不抛异常：坏 JSON、空文件、以及**合法 JSON 但不是对象**都要退回默认值。最后一种最容易漏——`5` / `true` / `null` / `[1,2]` 会让 `dict.update()` 抛 `TypeError`，而它**并不被 `except ValueError` 覆盖**（`"abc"` 抛的恰好是 ValueError，所以只有它被接住，容错看起来「部分有效」）。字段层面同理：`timeout` 必须是大于 0 的数字（`bool` 是 `int` 子类，需显式排除，否则 `true` 会静默变成 1 秒超时），文本字段必须是非空字符串。写盘一侧也只保存通过校验的值，不把界面上的非法输入留到下次启动再踩。

**校验要发生在「保存」之前**：设置对话框调用 `check_config()` 取一条人类可读的描述，就地显示在对话框里并**保留对话框**（用弹窗会把对话框关掉，用户得重填一遍）。否则填错的地址要等到下一次查词失败才暴露，那时用户早已忘了自己改过设置。`build_endpoint()` 也补了类型与协议两道闸，把「漏写 `https://`」变成一句人话，而不是让 httpx 抛 `UnsupportedProtocol`。

**线程模型**：所有网络请求经由 `QThreadPool` 派发，结果通过 Signal 回到主线程。切勿在主线程直接发起 HTTP 请求，否则界面会失去响应。

**后台任务的生命周期必须由 Python 侧掌握**：`QThreadPool.start()` **不持有** Python 包装对象的引用，而 `submit()` 的返回值在本项目里是被丢弃的。若不在模块内持有，包装对象会被立刻回收，挂在它上面的 `signals` 随之销毁，此时仍排在主线程队列里的结果投递会**全部作废**——现象是「任务确实跑完了（库里都写了），界面却毫无反应」，而且取决于 GC 时机，属间歇性故障，极难复现。因此 `submit()` 用 `setAutoDelete(False)` 关掉 Qt 的自动删除，把任务登记进 `_ACTIVE` 集合并于完成后移除。另注意：**接收者是普通函数 / `lambda` / `functools.partial` 时，投递依赖发送者存活**；只有 `QObject` 的绑定方法才由接收者一侧承载。压测 200 次可稳定复现 0/200 的丢失。

**只有最新一次请求的结果才允许上屏**：异步返回顺序不保证与发起顺序一致，先发的慢请求可能后到。没有这道闸门时，旧结果会把界面「抢」回上一个词条——而输入框已经清空，用户根本察觉不到自己看的是别的词。因此每次内容请求（查询 / 重新查询）都领一个自增序号，成功、失败、收尾三类回调一律先校验序号，过期的一律静默丢弃（过期的失败也不弹窗，因为用户已经在等新结果了）。

**错误重试策略**：只有**暂时性**故障才重试——网络错误、限流（429）、服务端错误（5xx），重试两次并退避。**确定性**故障立即抛出：鉴权失败（401）、地址错误（404）、模型名或参数有误（400 / 422）、权限或地区受限（403）、额度不足（402）。模型名写错这类问题再试一百次结果都一样，重试只是白等一轮。

**错误提示面向用户而非开发者**：网络层异常会被翻译成可读中文（超时不再显示成 `timed out`），状态码错误会从标准错误信封 `{"error": {"message": ...}}` 里取出人话，再拼上中文的排查方向，而不是把整个 JSON 倾倒给用户。响应体不是 JSON 时（例如网关返回 HTML 错误页）会剥掉标签后退回纯文本摘要。

**不完整词条为何要显式提示**：详情面板对空字段是直接不渲染的，于是「接口没返回同义语」与「这个词本来就没有同义语」在界面上完全一样。不把缺项说出来，用户就会把不完整当成结论，最后连缺项一起打印出来背。因此 `Entry.missing_parts()` 会指出缺了什么，详情区顶部与状态栏都会提示。**完全空壳**（连一种语言的释义都没有）则直接拒收、不入库——存进去只会在生词本里留下一条空白记录，还会被一并导出打印。

**备注与标签是用户自有字段，接口回填不得覆盖**：`Repository.upsert()` 以 `entry.id` 是否为空区分两种语义——`id` 为空表示「刚从接口取回的新内容」，此时若库中已有同 lemma 词条，**保留库里的备注与标签**并把保留结果回写到内存对象（界面渲染与索引同步都依赖它）；`id` 已就绪则表示调用方做过「读取-修改-写入」，全部字段生效。若不区分，点一次「重新查询」就会把用户写的备注静默抹掉（全文索引一起失效），且无法恢复。反过来，用户显式清空备注也走读取-修改-写入，因此仍然生效。

**`refresh()` 与 `lookup()` 的返回契约不同**：`lookup()` 返回 `(entry, cached)` 元组，`refresh()` 只返回 `Entry`。界面层两者各用一个回调（`_on_lookup_ok` / `_on_refresh_ok`），共用 `_present_entry()` 呈现。历史上曾把两个都接到同一回调，导致 `TypeError` 被吞成「查询失败」提示——而数据库其实已经更新成功，只有界面以为自己失败了。

**打包裁剪的两条规则**：

1. **删库必须连同孤立插件一起删。** Qt 插件会引用对应的 Qt 库，只删库不删插件会留下断裂依赖——程序不会报错，而是直接起不来窗口，且 `--selfcheck` 依然全绿（自检不进入渲染路径）。例如 `qsvgicon.dll` 依赖 `qt6svg.dll`、`qpdf.dll` 依赖 `qt6pdf.dll`。`scripts/check_trim.py` 就是为检出这类问题而写的。
2. **Python 的 OpenSSL 不可删。** `libcrypto-3.dll` / `libssl-3.dll` 看似只服务 Qt WebEngine，但 Python 3.12+ 的 Windows 官方构建已改为动态链接 OpenSSL，移除后 httpx 的 HTTPS 会全部失败。`--selfcheck` 中的「Python SSL 可用」一项用于守住这条底线。
3. **图标要同时出现在两处。** `Quill.spec` 里 exe 的 `icon=` 决定资源管理器里显示什么，`datas` 决定窗口图标能否加载（`app/main.py` 打包后按 `assets/quill.ico` 查找）。只写前者会得到「exe 有图标、窗口没有」的割裂状态。`--selfcheck` 中的「图标可被 Qt 解析」一项用于守住这条。

**离线词库为什么自己构建，而不直接用 ECDICT 原库**：三个原因——体积（131 MB → 11.6 MB）、
字段冗余（`sw` / `collins` / `bnc` / `frq` 服务于分词排序，对「查一个词看释义」是纯冗余）、
以及原库缺少覆盖全量的「屈折形态 → 原形」索引（`focus_word_forms` 只有 4.7 万条）。
查 `running` 要落到 `run`，只靠规则还原会出现同形碰撞（`news` → `new`），
而用词典自带的 `exchange` 字段反向建表是把这件事交回给数据本身。此外源语料的例句
约有 9% 配对错误——同一个句子被挂到了多个毫不相干的词下（`I hope we'll be home for
Christmas` 同时是 abiding / absorbing / accommodating / running 的例句）——构建时会逐条
校验句子是否真的用到了该词，不匹配的直接丢弃：**把错的例句当成「该词的用法」展示，
比不给例句更糟**，用户会照着它记住一个不存在的搭配。

**「缺项」提示必须区分来源能力**：详情面板对空字段是不渲染的，所以缺项要显式喊出来。
但离线词库结构上就不含同义语，若照喊，每一条离线词条底下都会挂一句「缺少同义语」——
提示一旦恒定出现就等于没有提示，用户会连真正的缺项（接口这次少给了一条例句）一起忽略掉。
因此 `providers/base.py` 的 `PROVIDER_FIELDS` 声明各来源结构上能提供什么，
`Entry.missing_parts(provided)` 据此过滤；未知来源按「全都能给」处理——宁可多喊一次，
也不要把真缺项藏起来。

**离线词库随包分发这件事必须被断言守住**：漏掉 `datas` 里的词库文件，程序**不会报错**，
只会表现成「离线模式查什么都说未收录」——看起来像词库太小，实际是文件根本没被打进去。
`run.py --selfcheck` 里的「离线词库随包分发」就是为这条写的，它必须在**打包产物内**运行才有意义。

**「算不算中文」只能有一份定义**：同一个汉字范围，构建时决定源语料那一侧收不收，校验时
决定收下的是不是合格。它曾被实现成两份——Python 正则一份、SQLite GLOB 一份——而注释写着
「两处保持一致」。实测不一致：Python 侧上界 U+9FFF，GLOB 侧写的是 `[一-龥]`（`龥` 是
U+9FA5），于是 U+9FA6–9FFF 的汉字会被 Python 放行、被 SQL 判成不合格，构建当场失败，
报的还是「例句中文侧不含任何汉字」这种指错方向的错。

那时把它收成了「构建脚本内部一份」（`CJK_START` / `CJK_END` → `CJK_GLOB_CLASS`），并把校验 SQL 提成 `FAKE_ZH_SQL` 供构建期与自检共用。**但那只解决了那个文件内部的分裂**：`db.py`、`repository.py`、`importer.py` 里仍各写着一份同样的字面量，四处合计**四份定义**，只是碰巧值相同。这正是这条约定最容易被绕过的形态——值一样，所以谁都看不出问题；改其中一处，检索就会与索引端对不上。

现在范围只在 `app/core/db.py` 定义一次（`CJK_START` / `CJK_END` → `CJK_CLASS`），四个消费方全部 import 它，构建脚本也不例外（脚本 import 应用代码在本项目有先例：它本来就 import `app.providers.offline.OFFLINE_SCHEMA_VERSION`）。**量词留在调用点**：`db.py` 提供 `_CJK_RE`（带 `+`，供 bigram 切分与 `strip_cjk`）与 `_CJK_ONE_RE`（不带，供导入解析确定「第一个汉字在第几位」），两者都从 `CJK_CLASS` 派生——只共享字符类、不共享量词，因为三个调用点对「一个还是一个连串」的需求本来就不同。

守这条的断言有五层，各自堵一个不同的漏洞：

| 断言 | 堵的是什么 |
|---|---|
| 汉字范围边界符合契约 | 端点值被改（含 U+4E00/U+9FFF、不含 CJK 扩展 A） |
| 校验用的 GLOB 与 has_cjk 结论一致 | 构建脚本内部 Python 侧与 SQL 侧分家 |
| **四处消费方共享同一份定义** | 有人改回「各写一份」——用 `is` 判**对象身份**，不是 `==` 比**值**：值相等太容易偶然成立，那恰恰是地雷当初的形态 |
| **汉字正则由 CJK_CLASS 派生** | `db` 内部把 `CJK_CLASS + "+"` 换回手写字面量——此时值完全相同，只有派生关系能发现问题 |
| **全仓不得有第五份字面量** | 将来某个新模块顺手再写一个（前四层全是「已知的四处」，新副本不会连上任何观测点）。用 `tokenize` 只扫**代码**，注释与文档字符串里提到该字面量属正当说明，不报 |

五层都经变异测试确认会失败。最后一层（全仓扫描）还做了双向自证：注入一份真代码副本 → 报红；只在注释/文档字符串里提到 → 静默通过。

> 这条扫描的**范围**本身也写成了断言（要求恰好覆盖本仓源码）。第一版用 `rglob("*.py")` 从仓库根扫，撞进 `.venv` 与 `_ecdict_src`，拿到 **2239** 个文件、光 `tokenize` 就耗 11.6 秒，整个自检超时到**一行输出都没有**——而「超时」看起来像环境卡顿，不像「我这处范围写错了」。后来把范围显式列成 `app/` + `scripts/` + 两个入口（36 个文件），并把「确实扫到了文件」写成**区间**而非下限：只验下限的话，「扫太多」它一句话都不会说。

**兜底为什么必须标注、以及为什么只挂在一处**：这两件事各有一次具体的返工。

- *标注*：初版让兜底静默发生——接口失败就用离线结果顶上，界面上看不出区别。后果是
  「接口失败」这件事从界面上消失了：用户看到释义就以为接口是通的，直到发现同义语
  一直空着才起疑，而那时他早已忘了自己改过配置。现在兜底产出的词条带真实来源
  （`source="offline"`）与失败原因（`fallback_reason`），详情区显式说明。
- *分层*：兜底挂在 `build_provider` 上，**不下沉进 `OpenAICompatProvider` 自己**。
  `http_smoke.py` 直接构造接口 Provider 来验 401 / 404 / 429 / 超时等失败分支，
  兜底一旦下沉，这些测试会安静地拿到离线结果——测试因为兜底而通过，而它本该守住的
  失败路径再没人跑。`selfcheck` 里「接口 Provider 自身不含兜底」这条断言就是钉子。

**兜底自己也没命中时，抛的是原始接口错误**，不是「离线词库未收录」。后者把一个可修复
的配置问题（密钥失效、地址写错、网络不通）伪装成词库容量问题，用户拿着它不知道该改哪里。

**「验了渲染」不等于「验了链路」。** 兜底提示最初只在 `gui_smoke` 里用手工构造的
`Entry(source="offline", fallback_reason=…)` 调一次渲染函数来验——那只能证明渲染函数
本身没问题，证明不了「接口失败 → 兜底 → 服务层写库 → 界面」这条链路上有没有人在中间
把字段丢掉。补上真实链路测试（把 `FallbackProvider(AlwaysFailingProvider(), OfflineDictProvider())`
塞进主窗口，真查一个词）之后，立刻暴露出 `_present_entry()` → `_reload_list(select_id=…)`
→ `_on_item_changed()` 会用 `Entry.from_row()` 重建对象覆盖详情区，把失败原因抹掉。
**手工构造的输入会绕过所有中间环节，因此它测的是最不可能出错的那一段。**

**配置文件新增开关字段必须登记进 `_COERCERS`**：`save_config()` 只保存 `_COERCERS` 里
出现过的字段。漏登记不会报错，只会表现成「在设置里关掉兜底、重启后又自己打开了」——
开关形同虚设且无从排查。`run.py --selfcheck` 的「兜底开关可保存且真正生效」同时验证
落盘与接线两侧。

**源语料的字面量换行必须解码，而且要在构建层解。** 这条和下面那条行尾事故**是同一类**：
都是在「处理换行」的代码里处理了**另一种表示**，于是看起来做了防护、实际什么都没做。
ECDICT 把换行存成两个字面量（反斜杠 + n），而 `clean_text()` 规整的是真换行 `\r\n` / `\r`——
对 58,542 处转义完全无效。后果不止「界面显示 `\n`」这么表面：词性正则的 `\b` 边界被破坏，
`run` 的词性从「n. / vi. / vt.」缩成「n.」。**派生数据被污染比显示错乱更难发现**，因为它
不写在脸上。所以新增一层清洗函数之后，必须验证它真的作用到了目标数据上，而不只是
「函数跑过了」。

**测试在失败路径上也必须能把结果报出来。** 「旧版词库被拒绝」这条断言原本写在
`tempfile.TemporaryDirectory` 里：守卫一旦被改坏，漏出来的连接占住文件，Windows 下清理
抛 `PermissionError`，进程异常退出把 stdout 缓冲一起丢掉——**断言一个字都没输出**，
现场只剩一个与主题无关的 `WinError 32`。**失败路径上的清理动作会毁掉失败现场。**
现在连接显式 `close()`；变异测试里那一项也随之从 `CAUGHT*`（崩溃）变成 `CAUGHT`（断言命中）。

**源码行尾统一为 LF，且这条由自检守住**：混用行尾不会让程序出错，但会让 diff 失去
意义——改一行显示成改了整个文件。本项目真实踩过一次：一个校验工具用
`read_text` / `write_text` 还原被临时修改的文件，而 Windows 上 `write_text` 会把 `\n`
翻译成 `\r\n`，于是「还原」悄悄变成改行尾，内容看着没变、字节全变。现在涉及文件改写的
工具一律走 `read_bytes` / `write_bytes`，`selfcheck` 里有一条扫描全仓的断言守住这条，
并且**额外断言「确实扫到了文件」**——扫描范围写错的检查永远绿。

## 为什么单实例锁要写得这么绕

`app/main.py` 的 `acquire_instance_lock()` 里有两处反直觉的写法，都是实测踩出来的，改动前请先读：

1. **完全不往锁文件里写内容。** 最初在加锁前先往文件里写一个空格，结果第二个实例启动时，`open(path, "w")` 会把文件截断并尝试写入偏移 0——而偏移 0 正是第一个实例已经锁住的字节区间，写入直接 `PermissionError`。锁的语义只需要「某个字节被占用」，不需要任何内容。空文件同样可以加字节锁（Windows 允许锁定超出文件末尾的范围）。
2. **用裸文件描述符，不用 `open()` 返回的缓冲对象。** 缓冲对象在 `close()` 时会再 flush 一次，一旦此前发生过写入冲突，`close` 自身会抛 `PermissionError`，把「已有实例」这条正常分支变成崩溃。

进程退出（包括被任务管理器强杀）时操作系统会释放文件锁，实测释放及时，因此不存在「锁文件残留导致再也打不开」的问题，也无需清理逻辑。

## 界面美化与窗口背景图

**美化的结论是「问题不在配色」。** 花了一轮先做诊断：「淡色 + 细边框 + 低饱和强调色」这条基底是成立的，没有需要推翻的东西。真正的毛病只有三条——**层级**（工具栏六个按钮视觉权重完全相同）、**对齐**（同义语 chip 宽度随词长变化，右侧释义起始位置参差）、**提示可读性**（三类提示都是「一行长句直接铺在正文底色上」）。方案见 `docs/ui-polish.md`。因此这些改动**没有动任何颜色常量**，只改「谁更显眼、边缘对不对齐、长句好不好读」。

落地后守住的几条：

- **工具栏分三级，视线才有落点**：主操作（查询，实心）→ 常规（导入 / 导出，描边）→ 次要（格式说明 / 备份 / 设置，无边框）。这是纯样式改动（挂 `objectName`），不动控件结构——界面测试断言的是文案与链路，样式可以自由换。
- **同义语 chip 拉成等宽**，让右侧释义成为一列。宽度**派生自当前这批词**（取最长的那个），不写死常量：写死时遇到 `conscientious` 这种长词，chip 会撑出省略号，比原本的参差更难读。另设 40% 上限保护——一个长词会把整列释义挤到下一行，那比「左边不齐」坏得多。
- **详情区底部的操作靠右收拢成一组**。弹簧原先夹在两个按钮中间，把它们甩到面板两端、中间空一大片，看起来像两个互不相关的按钮。
- **破坏性动作只在悬停时报警**：常驻报警会把「删除词条」喊成这一屏最显眼的按钮，而它恰恰是最不该被顺手点到的那个。同理，卡片右上角的 `×` 常驻色比正文占位文字再淡一档（但**不复用** `TEXT3`——那个常量还管着占位文字与两处禁用态，改它会把那几处的可读性一起拖下去）。
- **提示条从「一行长句」改成块**（缺项 / 兜底 / 陈旧三件套）。底色与面板白的对比只有 1.07，肉眼几乎看不出边界，所以**描边不能省**——块的形状全靠那 1px 定住。文字色与底色必须**同时**挑：原来的 `#9A6B2F` 在白底上是 4.65，落到提示块底 `#FCF7EE` 上只剩 4.36，跌破正文 4.5 的门槛——只加底色、不动文字色，可读性反而下降。自检里有一条**成对断言**盯着这件事：新色必须达标，**且被换掉的那个旧色在提示块底上确实不达标**（否则上面那条断言没有意义）。
- **背景透出档位的样式规则由档位表生成，不手写**。`theme._veil_rules()` 遍历 `BG_VEIL_LEVELS` 生成那几条 `rgba` 规则——手写两遍的话，改了常量而漏改规则**不会有任何报错**，只会静默地让某一档看起来和另一档一模一样。自检的守法是逐档去比：「每条规则里的不透明度必须等于表里那个数」，而不是只数「有没有一条半透明规则」。

### 背景图为什么不是「选张图铺上去」这么简单

四个坑，都是实测踩出来的，细节写在 `docs/window-background.md`：

1. **模糊不能用 `QGraphicsScene` + `QGraphicsBlurEffect`**。那套配方属于 QtWidgets，而 `app/ui/background.py` 只需要一个 `QGuiApplication` 就能干活；少了 `QApplication` 时构造它**直接段错误**——不是异常，是进程当场消失、连一行错误都打不出来（自检跑到那段直接 EXIT=139、零输出）。改用「降采样再上采样」的近似：一次「缩到 1/f 再放回」把像素摊成约 f 像素宽的过渡，两轮叠加近似高斯，全程走 Qt 的 C++ 实现。附带好处是它不取样到画布之外，没有边缘暗圈。
2. **模糊只算一次**。拖动窗口会不停换尺寸，每帧重跑卷积会明显发卡。所以模糊在固定工作尺寸（1600×1000）上做一次并缓存，之后各尺寸只做缩放——自检用打桩计数把「只算一次」变成可观测的断言。
3. **光把图铺上去不够，面板必须让位；而「让位」让到什么程度，第一版判断错了。** 首版做出来，背景图预览与主预览**几乎一模一样**——因为面板、列表全是白的不透明，图片只能从 16px 的页边距露出来，「换了背景」实质上看不出来。于是给 `#panel` 与 `QListWidget` 加半透明，并把不透明度**写死成 88%**。实测这一版仍然不成立：窗口里 94.4% 的像素确实因为背景图变了色，但饱和的纯红透上来只是 `(252,229,226)`——一层几乎看不出的色偏。用户的原话是**「那你不还是没有做出自定义背景图的功能吗，只是加了个蒙版」**。量化之后才看清：12% 的透出让图片在面板上只剩下均值偏移，看不出是「一张图」。所以现在把它做成**三档可选**（含蓄 88% / 适中 72% / 明显 58%，默认适中）——**装饰性功能做不到「一眼看得出」就是没做**，而合适的浓度随图而异（深色照片与浅色插画差很远），这个判断交给用户。三档都算过可读性下限：最坏情况（图那块正好是纯黑）下正文对比度分别是 12.5 / 9.8 / 5.4，全在 4.5 之上，所以调到最明显也不会读不清。**卡片刻意留在不透明这一侧**——试过让卡片也半透明，结果列表项自己的文字从卡片底下透出来成了鬼影（列表项文本是透明画的，一直靠卡片盖住），而把它改成透明色会毁掉无障碍接口与测试赖以读取的「这一行是什么」。
4. **祖先属性变了，后代选择器的缓存不会失效**。`QMainWindow[hasBackground="true"] QFrame#panel` 这类规则挂在**子控件**的样式缓存上；窗口自己的动态属性变了，**不会**让那些缓存失效——现象是「背景换了，可面板还是不透」，且不报任何错。所以除了窗口与状态栏，还要遍历 `findChildren(QWidget)` 逐个 `unpolish`/`polish`。

**验证方式也踩了坑**：`gui_smoke` 要证明「面板真的透了」，第一版读屏幕像素，两条断言都读到 `(255,255,255)`，看起来像功能没生效。探针给出的决定性证据是控件的**解析后调色板**——`panel.Window` 从 `(255,255,255,255)` 变成 `(255,255,255,224)`，说明 QSS 被正确解析了；但**离屏平台不做子控件半透明与父窗口图片的合成**（子控件半透明被画成纯白），读像素永远读到白，会得到一条**误导性的失败**。因此这两条断言改读 `QPalette` 的 alpha。背景图**本身**（画在窗口上、不是子控件）则可以用像素验：铺一张纯品红图判断留白处是不是品红，用棋盘图对比「清晰 / 模糊」——清晰版硬边跳变必须 ≥ 模糊版的 3 倍（**成对断言**是必须的：只写一条的话，一个「永远模糊」或「永远不模糊」的实现都能在单边上通过）。

## 标签、批量查词、撤销与测试连接（Round 27）

**标签的存储形态必须是确定的。** 库里的 `tags` 一律是**单空格分隔**
（`join_tags()` 一处归一）。不归一的话，按标签筛选就只能退化成 `LIKE '%考研%'`
——而子串匹配一定会在「某个标签是另一个的前缀」时出错：筛「考研」会把
「考研英语」一并带出来，两条都是真词条，用户以为自己筛错了。所以筛选的判据是
**解析出来的标签里有它**（`Entry.tag_list` → `models.split_tags`），不是字符串包含。
`split_tags` 是**唯一一份定义**，三个消费方（详情区输入框、按标签筛选、导入回填）
都走它——外部文件里的 `tags` 可能是逗号分隔的，界面写入的是空格分隔的，两种形态
在库里同时存在，各写一份解析就必然有一处漏掉某一种。

**筛选与搜索是「与」，不是「谁顶掉谁」。** 用户真实会做的是「在这个标签里找那个词」，
若后一个条件把前一个顶掉，他会以为标签被清空了。交集按 **id** 取，不能用词形字符串
去比——文字检索走 FTS（含大小写折叠与词形归并），`Ubiquitous` 与 `ubiquitous`
是同一个词条。

**一串词怎么收，和「整串本身是不是词条」是两件事。** 输入框回车时先做一次
**只读**的本地缓存判定（`DictionaryService.cached()`，绝不发网络请求）：整串已收录就按
词组查，否则按空白/逗号/分号/换行拆开，复用导入那条批量链路（分批、进度、取消、
「新增 / 已存在」统计全都在那里）。拆词的判据刻意**不复用标签那套分隔符**——标签允许
用空格分隔，而这里空格就是词的边界，两处长得像、语义相反。批量查词的报告口径也与
「导入文件」分开：从输入框粘进来的词说成「导入完成」，用户会去找自己什么时候导入了
文件。

**撤销为什么要清空 id——这条理由换过两版才站住。** 删掉一条之后状态栏出现
「撤销删除」，把整条 `Entry`（含备注、标签、收录变体）放回生词库。恢复走
`upsert()`，但 `entry.id` 先被清空。原先这里写的理由是「SQLite 会把删掉的行号分给
下一个新词条，带着旧 id 写回去会覆盖别人」——**取证后不成立**：`entries.id` 是
`INTEGER PRIMARY KEY AUTOINCREMENT`，SQLite 用 `sqlite_sequence` 记住用过的最大值，
行号不复用。换上去的第二版理由（「会 UPDATE 到一行不存在的记录、于是静默落空」）
**同样不成立**：`upsert()` 的查找条件是 `WHERE lemma = ?`，**根本不按 id 找行**。
站得住的是：`entry.id` 在这里唯一的用途是 `upsert()` 里 `entry.id is None` 那个
**分支开关**，它决定「同名声词条已存在时，备注与标签听谁的」。撤回来的是一份
**删除前的快照**，而删除之后用户完全可能又把这个词查了回来、并在上面写下新的备注；
保留快照的 id 会让它走「用户编辑过的对象」那一支，把用户新写的那句静默盖掉——两条
路径都会报「已恢复」。走「回填」那一支则只补内容、不碰用户字段，与本项目
「用户自有字段不被回填覆盖」那条铁律一致。

> **教训写在这里，因为它差点被漏掉：换掉一条假声明时，新理由同样要取证。**
> 两次都是断言把它抓出来的——第一版是被「删除后新插入的 id 不等于被删的那个」
> 抓住的，第二版是被「带一个不存在的 id 写回也会更新到那一行」抓住的。如果不写这两条
> 断言，我会用一个听起来更顺耳的谎替换掉原来那个谎，而**代码一行都不用改**。

**测试里的 `QMimeData` 必须活到事件用完为止。** `QDropEvent` 不持有它的 Python 引用，
在一个把事件构造封装成函数的辅助里，`mime` 会随函数返回被回收，`event.mimeData()` 于是
给出一个已析构的包装对象——报出来是 `'QObject' object has no attribute 'hasUrls'`，
看着像事件 API 用错了，其实只是生命周期。

**`QStatusBar.showMessage` 会盖住普通区（`addWidget`）的控件**，所以「撤销删除」按钮
放在**永久区**（`addPermanentWidget`）——否则它只在没有任何提示消息时才可见，而删除
之后恰恰必有一条提示消息。

**测试连接要发真请求，而不是只看配置格式对不对。** 它按**界面上当前填着的**地址 /
模型 / 密钥发一个最小请求（`max_tokens: 1`），把服务端原话就地显示出来，通了还回显
模型名。刻意不先要求保存：填完新地址的第一件事就是试它，若必须先保存才能测，测的
就不是刚填的那个值，而填错的地址一旦保存，下次查词就会用它。也刻意**不带
`temperature`**——推理型模型（`deepseek-reasoner` / R1 系列）不接受这个参数，带上会
直接 400，而那并不是配置错了。这件事靠一个只活在检查里的 stub 服务端守住：读它收到的
**真实请求体**，断言里面没有 `temperature`、`max_tokens == 1`、且带了 `Bearer` 头。
只用「不可达地址」验失败路径的话，成功路径那半边一条都不会被执行，而 payload 里到底
带了什么更是没有任何观测。

**这一轮的检查没有白写：它连工具自己的失配也抓出来了。** 锚点静态校验（唯一命中 +
变异后仍可解析）报出两条**早已过期**的变异锚点——一条是我这轮给 `repository.py` 的
导入行加了 `split_tags` 之后失配的，另一条是 `_html_escape` 改名时漏改的。它们此前
只会表现成 `[SKIP]` 并被计为「未抓住」，**看起来像保护失效，其实只是锚点过期**；
而误报比漏报更难查，因为它看着像证据。

## 固定搭配与词组收藏（Round 28）

**「已经是什么形态」要先判，再谈怎么解析。** `_json_list()` 要同时应付两种来源，
而这两种长得像、实际完全不同：`Entry.from_row` 拿到的是**库里的 JSON 文本**（是一段
字符串，必须 `json.loads`），`Entry.from_payload` 拿到的是**模型刚返回的 list**
（再 `json.loads` 一次会抛 `TypeError`）。第一版是一把梭地 `json.loads`，`except`
把 `TypeError` 吞成空列表——**搭配一条不剩地消失，而且不报任何错**：详情区安静地少了
一块，用户只会以为「这个词本来就没有搭配」。实测就是这么丢的（探针打出的封顶条数是
0）。修法是「能直接用的形态先用，剩下的才去解析」，并把非列表（`{"a": 1}` 这种）也
挡掉——直接迭代 dict 拿到的是**键名**，随后会被当成内容收下，产出「一条叫 phrase 的
同义语」这种谁也解释不清的东西。

**缺项提示按来源能力判，不是有则喊。** 离线词库（ECDICT）是「词 → 释义」语料，有释义、
约三成配了例句，但**没有固定搭配**——它是词典数据，不是搭配数据。照喊的话每条离线词条
都会挂一句「缺少固定搭配」，而**提示恒定出现就等于没有提示**，真正的缺项反而被淹没。
判据放在 `providers.base.PROVIDER_FIELDS`（该来源**结构上**能给什么），而不是看这条词
实际有没有。

**搭配刻意不进全文索引。** 它是**整表重建**的代价（加列 = 重建 `entries_fts`），而且
`FTS_WEIGHTS` 必须同步——长度不等会让 BM25 下标错位且不报错；`zh_bigram` 已经聚合了
全部中文，再挂搭配会把中文检索淹没。判据是「搜不到搭配是小事，搜索被噪音淹没是大事」。
词组收藏也**不建第二套 FTS**：词组是一条一条攒出来的，量级是几十，四个字段全读进来做
一次子串匹配比任何索引都快，而少一张 FTS 表就少一套「列集与主表对不上时整表重建」的
逻辑——那套逻辑在 entries 上必须存在，在 phrases 上纯属自找。

**词组收藏是第二张表，不是给 `entries` 加一个 `kind` 列。** 加列能省下一份导出路径，
代价是把 `count()` / `list_entries()` / `search()` / 导出上限判据全部牵进来——那一片正是
变异与消融重点守护的地方。更关键的是：**两张表各自从 1 发号**，`entries.id` 与
`phrases.id` 都是 `INTEGER PRIMARY KEY AUTOINCREMENT`，同一个数字在两边是毫不相干的两条
记录。所以删除与撤销的信号必须带**类别**（`("word", Entry)` / `("phrase", Phrase)`），
否则会安静地删掉（或覆盖）另一张表里的同号数据，而界面两种情况都显示「已删除 / 已恢复」。
检查里为此造了一次**真实的行号撞车**：把一条词组的 id 直接写成某条词条的 id，再删词条，
看同号的那条词组还在不在——不造这次撞车，「删词条之后词组还在」是一句近乎恒真的话，
没有任何分辨力。

**「含这个词」按词边界判，不是 `LIKE '%词%'`。** 子串匹配一定会误伤：`run` 会命中
`trunk`、`runway`、`brunch`。用户看到的是「这个词底下凭空冒出一串不相干的词组」，而且
没有任何提示说明那是子串匹配的结果。判据是逐词比较（`_contains_run`），多词词组照同一条
走——`ice cream` 在 `ice cream cone` 里算命中，在 `icecream` 里不算。

**词组详情不复用词条的渲染路径。** 词条那条路径里有备注与标签两个输入框，它们发信号时带
的是**词条的 id**；词组的 id 落进去会指到另一张表里的同号词条，而**两边都会显示
「已保存」**。所以词组有自己的 `show_phrase()`，底部只有一个「从词组收藏中移除」。

**加列必须登记 `ENTRIES_ADDED_COLUMNS`，而这件事本轮之前完全没有断言。**
`CREATE TABLE IF NOT EXISTS` 对**已存在**的 entries 表什么都不做，给老库加列只能靠那张
登记表。把 `collocations_json` 从登记表里删掉，全套检查照样全绿——而老用户从升级那一刻
起就丢掉了整块搭配内容。现在三件事一起验：DDL 与登记表指的是**同一个建列串**、旧库经
`init_db` 后真的补出了这一列、补完之后旧行读回来是**空列表**（不是 `None`、不抛）。

**除单词表外，六种导出全部带上搭配，理由是一条判据而不是顺手都加上**：搭配是用户花接口
额度换来的内容，任何一种导出把它丢掉都属于静默缩水。单词表不带是唯一例外：它只承担
「把词重新喂回来」，多一列就会让导入报告多出一批不是词条的噪音。CSV 的「固定搭配」列**只能追加在末尾**——
列顺序是对外契约，插在中间会让所有按列号解析旧文件的下游错位。JSON 新增字段**不递增
`JSON_VERSION`**（新增可缺省字段不是破坏性变化；新文件被旧版本读到只会忽略它），但改输出
结构**必须递增 `PROMPT_VERSION`**——否则存量词条不会显示「按旧标准生成」，用户会拿到一份
结构不同却不被告知的词条。`PROMPT_VERSION` 因此从 1 推进到 2。

**检查里捎带发现的两处缺口（都与本轮功能无关，但都属于同一类失效）。**
① `clean_temp.PREFIXES` 漏登记了三个临时目录前缀（`quill_tags_` / `quill_undo_` /
`quill_phrase_`）——它们分别属于 7b / 7e / 7f 三节建的临时库，全套检查跑了几十轮
**没有任何一条断言提到过它们**。原有的自证只验「前缀表取自本文件」，验不出「本文件自己
漏了前缀」；这正是「判据覆盖的目标恰好是被漏掉的那一类」的又一次兑现。现在改成**反向
核对**：把全仓 `mkdtemp(prefix=...)` 按 AST 扫出来逐个问表认不认，并用一张**故意认不出
任何东西的表**自证这条检查会失败。② 扫描器第一版用正则，被**它自己的文档字符串**里那句
示例绊倒，报出一个前缀 `'...'`——**判据抓错了对象**，改走 AST 才只认真正的调用。

**这一轮的检查也抓出了工具自己的失配。** 锚点静态校验报出 4 条**早已过期**的变异锚点：

## 托盘常驻、全局热键与全量词库（Round 32）

用户的三条决定把这一轮的方向定得很硬：词库直接放进安装包、热键用 `Alt+Q`、允许托盘
常驻但设置里能关。下面记的是三条决定各自的实现代价，以及实现过程中被检查抓出来的两
个真问题。

### 两键热键：`RegisterHotKey` 而不是键盘钩子

三键（`Ctrl+Alt+Q`）几乎不会冲突，但用户的场景是「读 PDF 时不想把手从键盘上挪开」，
每多一个键就是多一次手指位移。两键在 Windows 上就是「修饰键 + 主键」，而
`RegisterHotKey` 天然支持，且不注入任何进程、不需要管理员权限、不读取输入内容。

`Ctrl+Q` 不能当默认值：浏览器与编辑器普遍用它表示退出，抢走它等于弄坏别的软件。
`Alt+Q` 落在多数程序留给菜单的那一排，冲突最少。

**代价是注册独占，而且失败时静默。** 同一个组合键全系统只能注册一次，被别的程序占了
就返回 0。这属于「什么都没发生也不报错」那一类，所以注册结果必须被检查：失败时在
状态栏直说「被其他程序占用」，而不是让用户对着一个没有反应的热键猜。

组合键只写一份定义（`_MOD_NAME` / `_KEY_NAME`），显示文字与虚拟键码都从它派生。分成
两处写的话，改了显示而忘了注册，用户会按一个从来没被注册的键——而界面看起来一切正常。

### 托盘的前提，以及一个被造出来的死局

热键要能在窗口不在的时候工作，进程就必须活着。这与「关掉窗口就彻底退出、任务管理器
里不留进程」直接冲突，只能让用户选：默认常驻，设置里能关，关掉之后关闭窗口真的退出。

**但托盘不存在时绝不允许把窗口藏起来。** `QSystemTrayIcon.isSystemTrayAvailable()`
在某些会话（远程桌面、被策略禁用的桌面、本项目的 offscreen 测试环境）返回 false，
此时 `show()` 不会报错，只是没有图标。若照样执行「关闭 = 隐藏」，窗口会藏进一个不存在
的托盘：进程还活着、数据库锁还占着，而桌面上什么都没有；再双击 exe 只会被告知「已在
运行」。于是出现一个再也打不开的常驻进程。三道前置检查（配置开着、平台支持、托盘可用）
全部通过才建托盘，任一不满足就干脆不建——没有托盘、关闭即退出，是可接受的状态。

这个死局还有第二半：即便托盘正常，用户双击图标时窗口正藏着，第二个进程该说什么？
原来的单实例锁只会弹一句「已在运行」。现在第二个进程先经 `QLocalServer` 敲一下第一个
进程，敲通了就把它叫到前台，然后安静退出。

### 全量词库：换的不是容量，是「查得到」与「够不够详细」的分界

精选档 4.9 万词的收录标准是「考试词表 ∪ 高频词」。对英语专业，「我读到的词查不到」
是硬伤，而它恰恰不在那套标准覆盖的范围内。

换成全量档之后：词条 769,435（15.5 倍），体积 11.5 MB 到 64.8 MB。**容量与详细度不是
一回事**，这一点必须写进 README 而不是靠用户自己发现：约 4.9 万条字段齐全（音标 88%、
英文释义 89%），其余 72 万条大多只有一句中文释义；例句 14,747 条，在全量档的分母下覆盖
不到两成。所以详情区的来源标签写「离线待重查」——它同时说了「这条是本机给的」和
「接上接口会更好」。

#### 换档之后才浮出来的问题：屈折形态的替身条目

ECDICT 给大量屈折形态单独建了条目，`runs` 的释义就是 `n. 顺串；泻肚子（run的复数形式）`。
而查词的顺序是「先精确匹配，再查形态表」——这条不变量本身是对的（`running` 自己就是
词条，不能被还原成 `run`，否则词典里有的词反而查不到自己）。于是全量档里查 `runs`
命中的是那条薄释义，而不是 `run` 的完整释义。精选档没有这个问题，因为那些词不在考试
词表里，换档之前不可能发现。

修法是构建时删掉这些替身。判据取自**条目自己的措辞**（中文释义写着「（X的复数形式）」
「（X的过去分词）」），因为三个看着更结构化的特征都不能用：无音标的说法会被
`acclaimed`、`abnormalities` 证伪；「是别人的形态且无音标」会误删三万多条真词；英文
释义也不干净（`imp. & p. p. of Act`）。实测命中 1,176 条，删掉后 `forms` 里的
`runs → run` 仍在，查词落到原形，精确匹配优先那条不变量毫发无损。

这个 bug 是被自检抓出来的（`离线查词经形态表落到原形 runs`），不是被 review 看出来的。
它说明一件事：**换数据源同样是一次代码改动**，全套断言的适用范围要重新想一遍。

#### 打包配置里的第二颗雷

单实例唤醒用 `QLocalServer`，而 `Quill.spec` 的 `EXCLUDED_MODULES` 里正好有
`PySide6.QtNetwork`（底层的 `qt6network.dll` 却因为触摸插件依赖而保留着）。源码运行
一切正常，打包之后 `import PySide6.QtNetwork` 直接失败——表现是「双击图标没反应，
只弹一句已在运行」。

这类问题只有在产物里才会暴露。所以 `run.py --selfcheck` 新增两项：全量词库真的随包
分发（`tier == full` 且词数达标）、`QtNetwork` 绑定可用。前者守的是「词库漏打进去
只表现成离线查什么都未收录」那类沉默故障，后者守的正是这一次踩到的坑。
