> `mutation_check` / `ablation_check`）。
>
> 这是 Round 25 在界面美化（见 `docs/ui-polish.md`）之外新增的一项功能，Round 26 补上了
> 「拖拽添加 / 最近使用 / 预览条」与面板外裸文字的垫底。本文记的是**设计与取舍**，
> 不是使用说明（使用说明在 README 的「功能」一节）。主题换色另见 `docs/theming.md`。
>

> 那一节记的就是「看得见」是怎么变成一条可测量的判据的。

## 一、它做了什么

| 配置键 | 默认 | 含义 |
|---|---|---|
| `background_image` | `""` | 背景图路径，留空表示不用。存**绝对路径**，程序不拷贝文件——用户换图只改路径，不必先「导入」一份 |
| `background_blur` | `True` | 是否给背景图加模糊蒙版。关掉即原图直出 |
| `background_veil` | `"medium"` | 背景从内容面板后面透出多少：`soft` / `medium` / `bold` |
| `background_recent` | `[]` | 最近用过的图（最新在前、去重、上限 6 条）。只存路径 |

**三条换图的路径**，因为「换一张背景」不该只有一种走法：

1. **把图片拖进窗口**——最省事的一条。拖拽落点同时也是「导入生词表」的落点，
   所以按后缀分派（先看图片），并且**先问一句**才改配置：同一个手势在两种文件上做两件
   完全不同的事，而「把我刚拖进来的照片写进配置文件」是用户没有要求过的副作用。
2. **设置 → 窗口背景**：路径输入框 + 「浏览…」+「清除」+ **「最近使用」下拉框**
   （只列文件名，完整路径进悬停提示，免得一个长路径把这一行撑爆），下面一个
   「加模糊蒙版」复选框、「背景透出」三档下拉框。
3. **预览条**：设置里那块 224×64 的横条走的是**同一个 `BackgroundRenderer`**
   （缩放 → 模糊 → 蒙版三步完全一致），所以它演示的不是「大概」，而是窗口里那一块的
   样子。它跟着图 / 模糊开关 / 档位 / **主题**任何一项变化重画——主题换了蒙版底色也换，
   不重画的话它演示的还是上一套的底色。

再下面一行是**就地说明**：当前用的是哪个文件 / 找不到文件 / 留空，以及模糊与档位。

> **预览条是「判据要落到看得见上」这条教训的直接产物。** 第一版把面板不透明度写死 88%，
> 结果功能齐备、断言全绿、94.4% 的像素确实变了色，用户的原话却是「这不是只加了个蒙版吗」。
> 若预览条当时就在，这个误判在设置界面里会当场暴露。背景图与透出档位的完整由来见本文
> 第三、四节；主题换色见 `docs/theming.md`。

**模糊默认开**：照片直接铺在界面后面通常太吵，糊一层既保留氛围又不跟正文抢注意力。
但开关**必须留给用户**——本身就很淡的图直出比糊了更好看，而这件事只有用户自己知道。

**透出档位默认取中间那档**，不取最含蓄那档。理由见第五节：最含蓄那档的实际效果是
「界面糊了一层纱、但看不见我的图」，那等于功能没做。档位**必须**给用户，因为合适的
浓度随图而异：深色照片要淡一些才不吵，浅色插画要透一些才看得见，而程序猜不准。

没有选图时那两个控件**一起置灰**（同一个判断点，不是两处各判一次）：
留着可勾选等于承诺一件做不到的事。

## 二、四条设计约定

### 1. 失败必须安静

背景图是装饰。路径失效、文件损坏、格式不支持，都只表现成「没有背景」——
**绝不抛异常、绝不拦住窗口启动、也绝不拦住配置保存**。

用户把图片挪了个位置，不该让程序打不开；软件打不开，他也就没有界面可以把设置改回来了。
同一条考虑写在 `app/config.py` 的容错原则里：装饰性字段不值得拿可用性去换。

这条落到三处：

- `BackgroundRenderer.set_source()` 把「文件不存在」「不是图片」「读不出来」一律归成
  返回 `False`，不抛异常（`Path.is_file()` / `QPixmap()` 的 `OSError` / `ValueError` 都接住）。
- `check_config()` **刻意不校验** `background_image`。它管的是「拦住会让程序不可用的配置」；
  若图片路径失效也报错，用户挪一下图片就再也保存不了设置——**一个装饰把他的配置界面锁死了**。
- 加载失败时状态栏**如实说明**：「设置已保存，但背景图没能加载（路径或文件格式有问题），已忽略背景」。
  只说「设置已保存」会让用户以为背景换上了，然后对着一张没变化的窗口反复改设置。

### 2. 模糊只算一次

拖动窗口边角会不停换尺寸。若每帧都重跑一遍卷积，拖动会明显发卡。

所以模糊在固定的**工作尺寸**（`WORK_SIZE = 1600×1000`）上做一次并缓存到 `_blurred`，
之后各窗口尺寸只做等比缩放。缓存之上还有第二层：上一次按窗口尺寸缩放出来的结果
（`_cache` + `_cache_key = (宽, 高, 是否模糊)`），因为拖动时同一尺寸会反复重绘。

自检里用打桩计数把这件事**变成可观测的断言**：换尺寸只应触发缩放，模糊次数恒为 1。
（「只算一次」如果只是注释里的承诺，改坏了不会有人知道。）

### 3. 缩放以「覆盖」为准（cover），不是「装下」（contain）

contain 在长宽比不匹配时会留白边，看起来像图片没加载完；cover 至少保证整幅铺满。

```python
ratio = max(size.width() / sw, size.height() / sh)   # max 而不是 min
```

取较大的那个比例，两个方向才都不小于目标；用 `min` 就成了 contain。
缩放后从中心对称裁掉多出来的部分，**返回的位图尺寸严格等于请求尺寸**，
调用方可以直接 `drawPixmap(0, 0, ...)`。

自检的判据是「六个取样点都不得是留白色」——只断言尺寸相等是不够的，
尺寸对但内容错位（比如从角上裁而不是从中心裁）照样是 visible bug。

### 4. 模糊只依赖 QtGui，不碰 QtWidgets

常见的那套配方是 `QGraphicsScene` + `QGraphicsBlurEffect`，但 **`QGraphicsScene` 属于
QtWidgets**，而本模块只需要一个 `QGuiApplication` 就能干活——`selfcheck.py` §18 就是这种环境
（它刻意只用 `QGuiApplication`，因为 `QCoreApplication` 升级不了）。

少了 `QApplication` 时构造 `QGraphicsScene` 会**直接段错误**——不是异常，是进程当场消失，
连一行错误都打不出来。**实测踩过**：自检跑到背景图那一段直接 EXIT=139、零输出。

改用「降采样再上采样」的近似：一次「缩到 1/f 再放回原尺寸」把每个像素摊成约 f 像素宽的
过渡，两轮叠加已足够接近高斯（`factor = max(2, radius // 2)`，两轮相同）。全程走 Qt 的
C++ 缩放实现，比在 Python 里逐像素卷积快几个数量级。附带好处是它**不会取样到画布之外**，
所以没有「四条边向内扩散出一圈暗边」的问题。

模糊半径按图片高度派推（`blur_radius_for`：`height / 70`，夹在 8–48）：写死一个像素值会随
尺寸变味——同一个半径在 4K 图上几乎看不见，在缩略图上又把画面全糊掉。

## 三、界面让位：为什么面板要转半透明，而卡片必须不透明

光把图片画在窗口上是不够的。**首版做出来，`preview_background.png` 与 `preview_main.png`
几乎一模一样**——因为面板、列表、卡片全是不透明的白，图片只能从 16px 的页边距和分割条
这些缝里露出来，「换了背景」这件事实质上看不出来，功能等于没做。

所以配了背景图时，主要的面要转半透明，让图片透上来。下面是**默认主题（浅色底座）**
下 `soft` 档实际生成出来的五条（`night` 那套底色的值与颜色都不一样，见 `docs/theming.md`）：

```css
QMainWindow[hasBackground="true"] { background: transparent; }
QMainWindow[hasBackground="true"][bgVeil="soft"] QFrame#panel      { background: rgba(255, 255, 255, 88%); }
QMainWindow[hasBackground="true"][bgVeil="soft"] QListWidget       { background: rgba(242, 242, 239, 88%); }
QMainWindow[hasBackground="true"][bgVeil="soft"] QStatusBar        { background: rgba(251, 251, 250, 88%); }
QMainWindow[hasBackground="true"][bgVeil="soft"] QPushButton#bare  { background: rgba(255, 255, 255, 88%); }
QMainWindow[hasBackground="true"][bgVeil="soft"] QLabel#countLabel { background: rgba(255, 255, 255, 88%); }
/* 这三条 × 三档，全部由 theme._veil_rules() 从档位表生成，没有一行是手写的 */
```

五个目标各自的颜色取自调色板里的现成值（面板取 `surface`、列表取 `track`——它本来就比
面板暗一档，两者同用一个白值会让列表底和详情面板齐平、卡片边界糊掉；状态栏取 `bg`），
所以换主题时它们自动跟着走。

两个属性选择器**缺一不可**：`hasBackground="true"` 表示「确实配上了可用的图片」，
`bgVeil` 才是档位。只写 `bgVeil` 的话，没配背景图时属性照样在那儿（档位总有默认值），
面板会平白无故变成半透明、把窗口底色透出来。

**这些规则是生成出来的，不是手写的**：档位名与不透明度只有 `BG_VEIL_LEVELS` 那一份定义。
手写两遍的话，改了常量而漏改规则**不会有任何报错**，只会静默地让某一档看起来和另一档
一模一样。自检逐档去比「规则里的不透明度必须等于表里那个数」，而不是只数「有没有一条
半透明规则」——后者在「三档全都写 88%」时照样会通过。

状态栏也必须跟着让位——它是窗口的直接子控件，不让位就会在底部压出一条不透明的横带，
看起来像背景图没铺满。

### 卡片刻意留在不透明这一侧

**试过让卡片也半透明，结果列表项自己的文字从卡片底下透出来，变成一层鬼影。**
原因是列表项文本（`_list_text`）一直是**透明画的**，靠不透明卡片盖住它。

把它改成透明色来消除鬼影会毁掉无障碍接口与测试赖以读取的「这一行是什么」，代价更大。
所以卡片保持不透明，图片照样能从卡片之间的缝（透明的轨道衬底）透上来。

守这条的是一条**反向断言**：卡片在背景图下**必须仍然不透明**；变异测试里也有一条
把卡片改成半透明，确认测试真的会报警。

## 四、让图片真的看得见：一次量化

半透明给了，功能还没成——**用户看不见就等于没做**。

### 第一步：先量「变了多少」

探针把同一窗口渲染两次（不配图 / 配一张饱和纯红图），逐像素比对：

```
窗口 1080x700  采样 756000 点
因背景图而可见变化的点：713800  (94.4%)

  左上边距       无背景=(251, 251, 250)  有背景=(230, 40, 20)
  左面板中部      无背景=(242, 242, 239)  有背景=(241, 218, 212)
  右面板中部      无背景=(255, 255, 255)  有背景=(252, 229, 226)
```

94.4% 的像素都变了——**这个数字会骗人**。真正要看的不是「变没变」，而是**变成什么样**：
饱和的纯红透上来只是 `(252,229,226)`，一层几乎看不出色偏的粉。12% 的透出把一张图的
明暗结构压成了均值偏移，「有背景」这件事在面板上根本读不出来。

### 第二步：把「看得见」变成可判定的量

判据不能是「用户觉得能看见」这种话。落到两个可测的东西上：

1. **三档必须真的不同**：逐档读控件的解析后 alpha，`soft/medium/bold = 224 / 184 / 148`。
   只断言「有一个半透明的面」是不够的——档位没接到样式上时（属性名写错、选择器少写
   一段），面板会**一直是同一个 alpha**，看起来一切正常，那个下拉框白做了。
2. **越明显越透，而最明显那档仍守住正文**：最坏情况（图那块正好是纯黑）下正文对比度
   `12.5 / 9.8 / 5.4`，都在 4.5:1 之上。自检里配了**成对断言**——「再往下调 15 个百分点
   就跌破门槛」，用来证明这个下限是真算出来的，不是随手挑的数字。

### 第三步：默认值不能取最保守的那一档

第一版把 88% 写死，效果是「界面糊了一层纱，但我的图呢」。默认因此改成中间档，并且
**用一条断言把它钉住**：默认档的不透明度必须比最含蓄那档至少低 10 个百分点，
否则「默认」与「最含蓄」在观感上分不出来——正是这次退化成「功能没做」的原因。

> 换一张**照片型**壁纸（有中间调、有明暗结构）复测，`medium` 档已经能明确看出天空、
> 地平线与绿坡压在面板后面，正文照样清楚。之前那次「看不出来」的判断，一半是被
> 极淡的测试图误导的——**样张本身不具代表性，结论就会指向错误的方向**。

### 第四步：如实写出代价

三档不是「都能用」，是「代价不同」。断言覆盖的是**正文**（`theme.TEXT`）。把**次要标签色**
（`theme.TEXT2 = #8A8A86`）也拿来量，`bold` 档的代价就露出来了。量法：在同一张照片壁纸下
逐档出图，统计面板区域内「次要标签色与该处背景的对比度 < 1.5:1」的面积占比——
这个占比就是「次要小字融进背景的面积」。

| 档位 | 次要标签融背景的面积占比 | 正文 |
| --- | --- | --- |
| `soft`（88%） | 1.2% | 达标（≥ 4.5:1） |
| `medium`（72%，默认） | 1.5% | 达标 |
| `bold`（58%） | **65.9%** | 达标 |

也就是说：**默认档随便用；`bold` 档在背景的中间调区域，英 / 中 / 例句 / 备注这类小字会与
背景融在一起。** 根因不在背景图这个功能本身——`TEXT2` 在白底上本来就只有 3.47:1
（`TEXT3` 2.09:1），这是「淡 + 细」基调的既有取舍；背景只是把它从「偏淡」推到了「看不清」。

处理方式：**不改调色板**（改了会破坏既有基调），把代价写进文档与 README，默认值取
`medium`。

`bold` 档后来（Round 26）补了一条样式分支：**只在最透那一档**，把直接压在面板上的次要
文字换成加深一档的 `text2_strong` / `text3_strong`。soft / medium 原样不动——动它们只会
无端把「淡 + 细」的层次压平。同一条分支里还补了**面板之外**两处裸文字的表面：工具栏那三个
无边框按钮与左栏的计数标签，它们的字原来直接压在**原图**上（浅色主题的次要文字落在图中间调
上趋近 1:1；深色主题的浅色文字落在图的亮部只剩 2.39:1）。换一个更深的文字色救不了明暗未知
的背景，只能给文字一个受控的表面——这正是状态栏当初的结论，当时只改了状态栏这一处。

详见 `docs/theming.md` 第五节。

复现判读用的出图命令（`QUILL_SHOT_WALLPAPER` 指向真实照片；自绘样张是无结构的低饱和
渐变，任何档位都只呈现一层淡色偏，会把人误导成「透明没生效」）：

```bash
W="C:/Windows/Web/Wallpaper/Windows/img19.jpg"
QUILL_SHOT_KIND=background QUILL_SHOT_WALLPAPER="$W"   .venv/Scripts/python.exe scripts/screenshot.py preview_background.png
QUILL_SHOT_KIND=background QUILL_SHOT_WALLPAPER="$W" QUILL_SHOT_VEIL=soft   .venv/Scripts/python.exe scripts/screenshot.py preview_background_soft.png
QUILL_SHOT_KIND=background QUILL_SHOT_WALLPAPER="$W" QUILL_SHOT_VEIL=bold   .venv/Scripts/python.exe scripts/screenshot.py preview_background_bold.png
```

## 五、Qt 的一个坑：祖先属性变了，后代选择器的缓存不会失效

`QMainWindow[hasBackground="true"] QFrame#panel { ... }` 是**后代选择器**，它挂在
**子控件**的样式缓存上。窗口自己的 `hasBackground` 动态属性变了，**不会**让那些缓存失效。

实测现象：背景换了，可面板还是不透——而且**不报任何错**。

所以 `_apply_background()` 里除了给窗口与状态栏设属性，还要遍历 `self.findChildren(QWidget)`
逐个 `unpolish` / `polish`。子控件数量有限（百来个），只在这一刻重算一次，代价可以接受。

这条也有独立的消融项（A16）：把 `findChildren` 那一段抽掉，面板立刻退回不透明。

## 六、验证方式：为什么读「调色板 alpha」而不是「屏幕像素」

`gui_smoke` 要证明「配了背景图之后面板真的透了」。第一版读屏幕像素，两条断言都读到
`(255, 255, 255)`，看起来像功能没生效。

探针给出的决定性证据是控件的**解析后调色板**：

```
无背景   panel.Window (255,255,255,255)  list.Window (242,242,239,255)
有背景   panel.Window (255,255,255,224)  list.Window (242,242,239,224)
```

alpha 224 = 88%，说明 QSS 被正确解析了。但**离屏平台（`QT_QPA_PLATFORM=offscreen`）
不做子控件半透明与父窗口图片的合成**——子控件的半透明底色被画成纯白，所以读像素
永远是白的，会得到一条**误导性的失败**。

因此断言改读 `QPalette.ColorRole.Window` 的 alpha，并在注释里写明为什么不读像素。

背景图**本身**（画在窗口上，不是子控件）则可以用像素验：`gui_smoke` 把一张纯品红图铺上去，
抓窗口位图判断留白处是不是品红；用棋盘图（64px 格子）对比「清晰 / 模糊」，清晰版硬边跳变
必须 ≥ 模糊版的 3 倍。**成对断言**是必须的——只写一条的话，一个「永远模糊」或「永远不模糊」
的实现都能在单边上通过。

> 棋盘格子用 64px 而不是更小：格子太小的话，把图缩放到窗口尺寸这一步本身就是一次平滑，
> 硬边先被缩放抹钝，模糊前后的差别随之缩到判不出来（实测 16px 格子在 600px 目标下
> 只有 55 → 31，比值 1.77，跌破门槛）。格子够大，缩放基本不改变硬边，测到的才是模糊
> 本身的贡献。

## 七、参数与边界

| 常量 | 值 | 为什么是这个值 |
|---|---|---|
| `WORK_SIZE` | 1600×1000 | 模糊在它上面做一次；决定「看起来有多糊」，与窗口大小无关 |
| `MAX_SOURCE_EDGE` | 8000 | 源图长边上限。再大的图既占内存，也让那唯一一次卷积变成秒级操作，而它在屏幕上不可能比窗口更清楚 |
| 模糊半径 | `height / 70`，夹在 8–48 | 按比例推，观感才与尺寸无关 |
| `_VEIL_LIGHT` | 88 / 72 / 58（%） | 浅色底座。三档都压在**纯黑**之上算过：正文对比度 12.5 / 9.8 / 5.4，全部 ≥ 4.5:1。再往下 15 个百分点就跌破门槛——这是真的下限，不是随手挑的数（见第四节） |
| `_VEIL_DARK` | 96 / 84 / 72（%） | 深色底座。最坏情况**反过来**——深色底座下正文是浅色的，怕的是图那块**纯白**。同一个 58% 在深色下只剩 3.2:1，所以整表上调。档位**名**两边共用（用户选的是一件事），**值**按底座分家（实现上必须不同） |
| 默认档 | `medium` | 不取最含蓄那档：那一档的观感与「没配图」几乎分不出来（见第四节）。深浅两边都是 |
| 每个档位的规则数 | 5 | 面板 / 列表 / 状态栏 / 裸按钮 / 计数标签。断言里的 `_per_level` 从目标表推出来，往后加一处目标只用改一个地方 |
| 面板 alpha 断言 | `255 > soft > medium > bold > 100` | 不写死具体数字：写死就把「调档位」变成一件会弄红测试的事；区间只守住「三档互不相同」与「还留着透明度」这两件事 |

## 八、失败模式一览（都经测试守住）

| 场景 | 期望行为 | 谁守 |
|---|---|---|
| 路径留空 | 窗口用默认底色，属性翻回 false | `gui_smoke`「清除背景后属性 / 底色」 |
| 路径不存在 | 不抛、不拦保存；窗口无背景；状态栏如实说明 | `selfcheck` §27③、`settings.py` 就地说明 |
| 文件损坏（内容不是图片） | 归成「没有背景」 | `selfcheck` §27③ |
| 图片特别大（> 8000px） | 先缩进来再处理 | `selfcheck` §27③ |
| 用户关掉模糊 | 出原图 | `gui_smoke`「背景图模糊对比」、`selfcheck` §27⑤ |
| 用户换档位 | 三档的透出程度必须真的不同 | `gui_smoke`「各档位的面板不透明度」、消融 A17 |
| 档位调到最「明显」 | 正文仍可读（对比度 ≥ 4.5:1） | `selfcheck`「最「明显」那一档仍守住正文对比度」 |
| 档位名写坏 | 退回默认档，窗口照常有样式 | `selfcheck`「不认识的档位一律退回默认档」 |
| 改了档位表忘了改规则 | 规则由表生成，不可能不一致 | `selfcheck`「规则里的不透明度由档位表生成」 |
| 拖动窗口改尺寸 | 只缩放、不重跑模糊 | `selfcheck` §27④（打桩计数） |
| 属性变更 | 窗口 / 状态栏 / 子控件样式全部重算 | `selfcheck` §27⑥、消融 A16 |
| 图片比窗口窄 | cover 铺满，不留白 | `selfcheck` §27① |
| 把图片拖进窗口 | **先问一句**，同意才改配置；拒绝则配置与最近使用都不动 | `gui_smoke`「拖入图片会先问一句 / 拒绝后不改配置」、消融 A20 |
| 拖进来的图读不出来 | 状态栏如实说「没能读成图片，背景未变」，不谎报 | `gui_smoke`「同意后状态栏如实报」 |
| 拖进来的是词表而不是图片 | 仍走导入那条路（落点按后缀分派，**先看图片**） | `gui_smoke`「拖入词表仍走导入」 |
| 换回用过的那张图 | 「最近使用」里直接切；去重、最新在前、上限 6、非列表退空 | `selfcheck`「最近背景图：去空、去重、丢掉非字符串」等四条、消融 A22 |
| 清掉背景图 | 「最近使用」仍留着（那是历史，不是当前状态） | `gui_smoke`「清除背景后最近使用仍留着」 |
| 换了主题 | 蒙版底色与半透明颜色跟着换，设置里的预览条一并重画 | `selfcheck`「每套主题的每个档位都守住正文对比度」、`gui_smoke` 逐套主题对表 |
| 面板外直接压在原图上的文字 | 也拿到**受控的表面**（裸按钮 / 计数标签） | `selfcheck`「面板之外直接压在原图上的文字也拿到了受控的表面」、变异「裸按钮不再垫底」 |
| 拖动**多个**文件进窗口 | 目前只处理第一个，其余**静默忽略**（已知缺口，见 `docs/optimization-proposals.md` P0-4） | —— 未守 |

## 九、没做的事

- **不做纯色 / 渐变背景的选择器**。用户自己找一张图比预置几套渐变有用，而预置方案要额外
  维护一套 UI，收益不成比例。真想要纯色，一张纯色 PNG 就是。
- **不做「按窗口尺寸自动裁剪 / 位置微调」**。cover + 居中足够，加参数只会让设置界面变重。
- **不做图片缓存的磁盘存储**。缓存全在内存，程序退出即丢。背景图是氛围，重算一次模糊
  在本机是毫秒级的事，为此写一套磁盘缓存不值得。
